# オーナー要望の受領・実装フロー

目的: 要望を1件も落とさず、**オーナーが言った意味のまま**直す。
正本の台帳は `docs/owner_requests.md`（運用ルールも冒頭に書いてある）。

## Step 0 — 未完の拾い直し

作業を始める前に `docs/owner_requests.md` の冒頭〜直近セッションを読み、
未完（📥/🔧/⏸）が残っていないか確認する。残っていたら今回の作業と併せて報告する。

## Step 1 — 受領（📥）

- 要望が複数まとまって来たら**1件ずつ行に分割**して台帳へ 📥 で追記する。
  「5点報告」は5行。まとめて1行にすると反映漏れの温床になる。
- この時点ではまだ直さない。全件をリスト化してから着手する。

## Step 2 — 解釈の確認（意図の汲み取り）

各件について着手前に自問する:

1. **自分の言葉で言い直せるか**。「オーナーがゲーム画面で見た現象」→「コード上の原因仮説」の
   2段で言い直す。現象の再現箇所（どの章・どの画面・どの台詞）を特定できないなら、まだ理解できていない。
2. **過去に意図的に決めた仕様と衝突しないか**。CLAUDE.md の「やらない」節・
   「〜は廃止/差し戻し済み」の記述と突き合わせる。衝突するように見えたら、
   勝手にどちらかを選ばず **AskUserQuestion で選択肢つきで確認**する
   （例:「これは○○の差し戻しに見えますが、今回は例外として戻しますか？」）。
3. **要望の裏の目的は何か**。指示された手段が目的に合わないと気づいたら、
   手段だけ実装せず「目的は△△と理解した。だとすると□□の方が効く」と提案する。
   ただし判断はオーナーに返す。
4. 解釈が2通り以上あり結果が大きく変わる場合のみ質問する。
   些細な差はもっともらしい方を選び、**何を選んだか完了報告に明記**する。

## Step 3 — 実装

- 直すのは**正本のみ**（`web/` のソース＋`data/*.json`）。
  `web/js/data.js` と `web/dist/*.html` は生成物なので絶対に直接編集しない。
- 台詞・イベントを触る場合は **dialogue-edit スキル**のチェックリストに従う。
- 着手した件は台帳を 🔧 に更新。

## Step 4 — 横断確認（「直したはず」を信用しない）

✅ にする前に、**修正したファイル以外にも同じ症状が残っていないか grep で現物確認**する。

- 教訓: アダムのカタコトは dialogue では消えていたが `lime_messages.json` に残っていた。
- 台詞・文言系: `grep -rn "<症状の文字列>" data/ web/js/ --include="*.json" --include="*.js"`
- 見た目・CSS系: reel.css→style.css のような**連結・複製先へのドリフト**がないか確認する。
- 「オーナーの手元で古い」系の報告は、コードの先祖返りを疑う前に
  **配信物（GitHub Pages）が古い版のままの可能性**を先に確認する
  （タイトル右下のビルド版数刻印 `D.build` で照合できる）。

## Step 5 — ビルド・テスト・完了報告

1. `python3 tools/lint_dialogue.py`（台詞を触った場合。ERROR=0 必須）
2. `python3 web/build_data.py && python3 web/build_standalone.py`
3. 変更に対応するヘッドレステスト（対応表は **web-build-test スキル**）
4. 台帳を ✅＋コミットSHA に更新（判断待ちは ⏸＋理由）。
5. 完了報告は**オーナーがゲーム内で確認できる形**で書く
   （「○章の△の場面でこう変わる」）。内部関数名だけの報告はしない。
