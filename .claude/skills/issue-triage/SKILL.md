# Issueを最新状態に整理する

## 正本と範囲

最初に対象refの [AGENTS.md](../../../AGENTS.md) と [現行資料ガイド](../../../docs/current_documentation_guide.md) を読む。最新のユーザー指示・当該作業に適用できる取得済み承認を優先する。過去の採用・通信・マージ許可を別件へ一般化しない。

整理の依頼ではIssueの現状と残件を整理する。「確認だけ」なら読み取りだけ、「整理して」なら根拠を確認して既存Issueのチェック欄・残件を更新する。採否の判断、実装、PRのReady化・マージ、外部への連絡まで含むとみなさない。実装まで頼まれた場合は [issue-to-merge](../issue-to-merge/SKILL.md) に進む。

## 1. 対象と根拠を限定して読む

1. リポジトリと最新main SHAを確認する。指定Issueまたは指定された題材の一覧から入り、本文・最新コメント・関連Issueを読む。全履歴・全素材・全branchを取得しない。
2. 関連PRのopen/merged/closed、base/head、変更ファイルと残件を照合し、現行コードと正本の該当箇所で実装の有無を確かめる。closed未マージを実装済みとせず、古い「未実装」のチェック欄だけで再実装を提案しない。
3. 新しい採用・取り下げ・保留指示を読み、古いIssue本文や担当ラベルだけで判断しない。`docs/design/`・`docs/reports/`、候補画像の保存、Draft PR、調査コメントは採用の証拠にならない。
4. mainのCI（夜間を含む）、必要なら公開workflowの対象SHAを確認する。実装済み・マージ済み・公開済みを分け、公開待ちを実装残件に戻さない。

取得できない根拠は「未確認」とし、推測でチェックを付けたりIssueを閉じたりしない。権限拒否や通信制限は別経路・別アカウントで迂回しない。

## 2. 残件と次に進めるものを示す

| Issue・項目 | 状態 | 根拠 | 残件・再開条件 | 関連PR・変更先 |
|---|---|---|---|---|
| 対象の番号と具体的な項目 | 完了／作業中／依存待ち／判断待ち／明示保留／未着手／未確認 | 最新コメント・PR・コードへのリンク | 次に何が必要か | 同一ファイルの重複と依存を確認 |

- 「完了」は必要な受入条件を満たす根拠がある場合に使う。実装済みだが検証待ち・未マージならその状態を明記する。
- 着手候補は承認済み・未実装・保留なし・既存PRと重複なしのものから選ぶ。mainの未解消CI失敗はAGENTS.mdに従い優先する。
- 同じファイルを変更する未マージPRがあれば、既存branch継続・依存待ち・独立タスクを示す。予約・claim・worker台帳を作らず、古い予約や担当ラベルの取得・解放を待たない。
- 最新指示で解除されていない明示保留・未採用案を「すぐ着手可」にしない。全体整理の依頼を個別の保留解除とみなさない。

## 3. 既存Issueへ必要な整理だけ反映する

1. 元の依頼・決定の記録を残し、現在の残件と根拠を短く追記する。編集直前に最新本文・コメントを再読し、並行更新を消さない。
2. 確認できた完了部分だけチェックを更新する。部分対応PRには `Refs` を使い、残件や判断待ちがある親Issueを閉じない。
3. 全受入条件の完了を現行コード・merged PR等で確認できた場合だけ閉じる。重複Issueをまとめる場合は固有の残件を移して相互リンクし、参照元を失わせない。
4. 新規Issue・子Issue・ラベル・進捗文書を大量に増やさない。長期仕様は既存の正本へ、進行状況はIssue/PRへ置く。ユーザーの新しい要望の記録には [owner-request](../owner-request/SKILL.md) を使う。

完了報告には「整理・closeしたIssue／残件と保留／次に着手できる1件」を示す。実装・検証をしていない場合は、その実施済みと読める表現を避ける。

## 呼び出し例

- 「issue-triageで、#123を最新mainと関連PRに照らして整理して」
- 「Issueの残件と保留を確認して、次に着手できるものを1件選んで。今回は確認だけ」
