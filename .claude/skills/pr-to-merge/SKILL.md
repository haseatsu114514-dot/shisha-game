# PRをマージまで進める

最初に対象refの [AGENTS.md](../../../AGENTS.md) を読む。Git安全・保存・通信量・CIとマージ条件はそこを正本とする。最新のユーザー指示と今回に適用できる取得済み承認を確認し、過去の許可を別PRへ一般化しない。「確認だけ」「今回はPRまで」「マージ保留」を守る。依頼済みの作業を再承認させず、必要な修正も含めて進める。

## 1. 現状・依存・停止条件を読む

1. 対象PRの本文・最新コメント・レビュー・未解決スレッド、関連Issue、変更ファイル、base/head SHA、Draft状態、競合、必要な承認、CIを読む。候補探しでは指定範囲のopen PRを対象にする。
2. 明示保留・採用待ち・未完のDraftは、その条件が最新の指示で解消された範囲だけ進める。候補保存やCI成功を採用とみなさない。古い本文と新しいコメントが違えば現物も照合する。
3. mainの最新CI・夜間検査の未解消失敗はAGENTS.mdに従い優先する。古いHEADの失敗や成功に置き換わった実行を停止理由にしない。
4. 依存PRと同一ファイルのopen PRを確認する。既存branchで続きを行い、他担当の変更を上書きしない。mainに遅れているだけなら毎回取り込まない。予約制度・必須preflight・新workflowは追加しない。

## 2. 修正と現HEADの検証を完了する

- 未解決の実装・レビュー指摘に対応し、必要な正本・要望台帳を [owner-request](../owner-request/SKILL.md) に従って更新する。無関係な仕様変更へ広げない。
- [web-build-test](../web-build-test/SKILL.md) で変更・危険度に合う局所検証と関連回帰を選ぶ。対象HEADまたは未コミット差分・コマンド・結果を記録し、成功/失敗/timeout/cancel/未実施を分ける。
- 同じHEADの成功は再利用する。無関係な差分で過去の局所検証を失効扱いしない。レビューも新しい差分に適用できるか判断し、現在の承認要件は別に確認する。影響する修正・競合解消には必要な再検証を行う。
- Git Safetyを実行し、修正をまとめてcommit/pushする。PR本文を最終変更・検証・残件・依存・次の一手に合わせて更新する。未完はDraft、完成したらReadyにする。CI待ちだけを理由にDraftに留めず、採用待ちのDraftをCI目的でReadyにしない。
- 現行workflowを確認する。現行必須checkは `.github/workflows/ci.yml` の `CI / result`。Draftではbrowserが省略されるため、その緑だけで完成PRをマージしない。Ready後の実行で現HEADと必要なbrowser計画を確認する。
- CI失敗は現HEADのログで原因を分けて修正する。必須check省略、判定・assertion弱体化、自作承認、形式的なスレッド解決で条件を満たしたことにしない。
- CI待ちだけなら対象PR・HEAD・残る必須checkと再開条件を一度記録する。短間隔の照会や同じ報告を繰り返さず、独立作業を進める。継続できなければPRへ保留理由を保存する。未依頼の将来監視を作らない。

## 3. 依存順にマージする

1. 積み重ねPRは先行PRを完了してからmainへbaseを変更する。依存branch宛てへマージしてmain反映済みとしない。base変更・必要な競合解消後は差分・CI対象を再確認し、先行PRの古い緑を流用しない。先行PRを進める権限や採用判断がない場合は依存待ちとする。
2. マージ直前に最新指示・明示保留、base/head SHA、Ready状態、競合なし、現HEADの必須CI成功、未解決指摘なし、必要な承認を再確認する。条件を満たし現時点の権限で実行できるPRは速やかにマージする。
3. 可能なら確認済みhead SHAをマージ条件に指定する。HEADが変わったら差分とCI等を再確認する。admin/bypass/forceで保護・承認を回避しない。
4. 応答だけで完了とせず、PRのmerged状態・merge commitとmainへの反映を照合する。通信切断等で成否不明なら再実行前に状態を読み、未実行と確認できない限り重複実行しない。
5. 関連Issueの今回完了項目にPR/SHAを添える。全受入条件を満たす場合だけcloseし、残件・保留がある親Issueを閉じない。必要なら [issue-triage](../issue-triage/SKILL.md) で照合する。
6. 公開対象の変更なら既存deploy workflowの結果と対象SHAを確認する。マージ済み・公開済みを分け、公開待ちで実装をやり直さない。自分の未commit・未pushを確認する。

権限拒否・通信制限は別アカウントや別経路で迂回しない。拒否された操作・対象・理由・完了済み範囲・未実行/成否不明を報告して該当操作だけ止める。

終了報告はAGENTS.mdの形式で短く示す。

```text
MERGED: #PR / PENDING: #PR(理由・再開条件) / ISSUES: #Issue(残件) / BRANCH: branch / NEXT: 次の1手
```

## 呼び出し例

- 「pr-to-mergeで、#123のレビュー対応からマージまで進めて」
- 「マージできるPRを確認して。未採用の候補はそのままにして」
