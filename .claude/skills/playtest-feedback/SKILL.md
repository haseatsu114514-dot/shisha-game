# 初見プレイヤーなりきり感想

## 大原則: 「知らないふり」を徹底する

このスキルの価値は**開発知識を封印できるか**で決まる。なりきり中は:

- CLAUDE.md・brand の設定知識を**評価に使わない**。画面に出た情報だけで判断する。
- 「これは伏線だと知っている」から面白い、は禁止。**知らずに読んで引っかかりが
  あるか**（=伏線が初見でも「ん？」と残るか）を評価する。残らなければ伏線は機能していない。
- 用語（ハガル・吸い出し・蒸らし等）が**その時点までのゲーム内で説明されたか**を追跡する。
  未説明の専門用語で置いていかれたら、それが感想になる。
- ch1優勝の違和感（実力ではない）のような「仕込み」も、初見にどう見えるかだけを書く。
  「意図的な仕込みだから問題ない」という開発者の答え合わせは感想の後の別枠で。

## プレイの仕方

1. **プレイ順で体験する**。対象章の dialogue をイベント発生順に読み、日次ループ
   （バイト/訪問/練習/スロット/夜イベント）は `web/js/game.js` のフローで進行を追う。
2. 見た目・操作感・テンポが論点のときは、実際に動かす:
   `python3 -m http.server 8123` → playwright で操作＋スクリーンショット
   （`web/test/screenshots.mjs` の起動部が参考になる。テストを流用してもよい）。
3. **感情メーターを記録しながら進む**。イベントごとに「ワクワク/ふつう/だれてる」を
   メモし、「だれてる」が2連続した区間を退屈候補としてマークする。
4. 選択肢に出会うたび「選ぶ楽しさがあったか（迷ったか・結果に差を感じたか）」を記録。
5. ミニゲーム・大会は「ルールを初見で理解できたか」「負けた時に理不尽と感じたか」を記録。

## 感想レポートのフォーマット

1. **プレイ日記（時系列）**: 主要イベントごとに一言＋感情メーター。
   初見の誤解（「〇〇だと思って読んでた」）は貴重なデータなのでそのまま書く。
2. **退屈ポイント ワースト3〜5**: どこで・なぜだれたか（説明の連続/同じビートの反復/
   報酬が遠い/選択肢がない区間が長い 等）。「何分くらい相当」の体感も添える。
3. **良かったところ トップ3〜5**: 何が刺さったか。**壊してほしくない要素**として明記。
4. **引っかかり・疑問リスト**: 初見で理解できなかったこと・違和感。
   伏線として機能しているもの（気になって先が読みたくなる）と、
   ただの不親切（置いていかれる）を区別して書く。

## やらないこと・線引き

- **修正しない**。感想が成果物。オーナーが「直して」と言った分だけ、
  owner-request → dialogue-edit / portrait-fix 等のフローに乗せる。
- 感想と**バグ報告は分ける**。プレイ中に見つけた明確なバグ（改行崩れ・進行不能・
  表示ズレ）はレポート末尾に「バグ観察（別枠）」として列挙し、
  対応するときは owner-request の台帳に載せる。
- 感想は率直に書く。**オーナーへの忖度で「全部面白い」にしない**こと。
  退屈な区間が見つからなかったときは「今回の範囲では見つからなかった」と書き、
  代わりに一番弱い区間を挙げる。
