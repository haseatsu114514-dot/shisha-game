# Issueから実装・PR・マージまで

対象Issueの残件を確かめ、小さなタスクを一つずつ実装して完了まで進める。計画を出すだけで終えず、現在の依頼・権限の範囲で実行する。

## 正本・既存スキルとの分担

- 最初に対象refの [AGENTS.md](../../../AGENTS.md) と [現行資料ガイド](../../../docs/current_documentation_guide.md) を読む。Git安全、通信量、保存、CI・マージ条件はAGENTS.mdを正本とし、このスキルで上書きしない。
- 要望の解釈・台帳更新・横断確認は [owner-request](../owner-request/SKILL.md)、検証の選択は [web-build-test](../web-build-test/SKILL.md) を使う。台詞・画像等の実装には該当専門スキルを使う。本スキルはタスク間とIssue→PR→マージの進行を補う。
- 最新のユーザー指示と、この依頼に適用できる取得済み承認を確認する。過去の許可・採用判断を他のIssue、素材、操作へ一般化しない。スキルの呼び出しだけで保留解除や新たな公開範囲の許可を得たことにしない。依頼済みの作業を再承認させない。
- 「分解だけ」「PRまで」「これはマージしない」等の指定を終点として守る。実装依頼を全Issueの整理や仕組み作りへ広げない。

## 1. 現在地と着手可能な残件を確認する

[issue-triage](../issue-triage/SKILL.md) の手順で、今回の対象Issueに限って本文・最新コメント・関連PR・現行mainを照合する。実装済み、既存PRで作業中、依存待ち、判断待ち、明示保留、着手可を分ける。全体棚卸しの完了を着手条件にしない。

checkoutではAGENTS.mdのGit Safetyを実行し、他担当の変更を上書きしない。既存checkoutを再利用し、新規作業は最新mainから、保存済みPRの続きは既存branchで行う。Issue指定がなければ依頼範囲の承認済み・保留なし・重複なしの残件から、小さく完了できるものを選び理由を短く示す。未確認の根拠を推測で埋めない。

## 2. 小さなタスクに分ける

大きなIssueは半日程度で実装・検証できる単位に分ける。各タスクを次の形にし、最初に実行するものを示してそのまま着手する。

| タスク | 完了条件 | 主な変更先 | 依存・重複 | 検証 | 対応PR・状態 |
|---|---|---|---|---|---|
| プレイヤーに起きる変化を1件で記す | どの操作・場面で何が成立するか | 実在する正本のパス | 必要な先行タスク/PR、なければなし | 局所再現と必要な回帰 | 既存PRまたは未着手 |

- 手段だけの「コード修正」「テスト」ではなく、単独で完了を判定できる変更にする。保存・進行・共通処理を触るものは境界条件も完了条件へ入れる。
- 既存子Issueやチェックリストを再利用し、分割しただけで子Issueを大量作成しない。小さな分解はIssue/PR本文で十分。独立して追う必要がある場合だけ子Issueを作り親へリンクする。
- タスク表は作業中の会話と既存Issue/PRへ置く。新しい予約制度、進捗bot、スナップショットMD、必須preflightを追加しない。
- 結果を大きく変える曖昧さだけ確認し、その部分だけ保留する。採用待ちの案を自分で決めず、独立して実行できる承認済みタスクを続ける。

## 3. 実装・局所検証を行う

1. 選んだタスクと関連正本だけを変更し、owner-requestの台帳・横断確認を行う。台帳の状態は実装済み、検証待ち、マージ済みを混同せず、未完を残す。
2. web-build-testと [remake/README.md](../../../remake/README.md) から変更・危険度に合う検証を選ぶ。局所再現→必要な関連回帰の順に確認し、全章通しを毎回要求しない。データには関連リンタを使う。
3. 各結果に対象HEADまたは未コミット差分、コマンド・対象場面、成功/失敗/timeout/cancel/未実施を記録する。同じHEADの成功は再利用し、無関係な変更で過去の局所検証を無効にしない。影響する実装・競合解消を行った場合は必要箇所を再検証する。正式な現HEADのCI条件とは分ける。
4. 差分をレビューし、目的外の変更、判定の緩和、未完の完了扱いがないことを確認する。Git Safetyを再確認して区切りごとにcommit/pushする。未完はDraft PRで保存する。

## 4. PRを作成しレビュー・CIを完了する

PR本文には「何がどう変わるか／Issueと今回完了するタスク／検証と対象HEAD／依存PR・残件・次の一手」を記す。全件を満たす場合だけ `Closes #番号` を使う。一部対応なら `Refs #番号` と完了項目・残件を記し、親Issueを閉じない。

以後のReady化、レビュー対応、現HEADの必須CI・Draft時のbrowser省略の確認は [pr-to-merge](../pr-to-merge/SKILL.md) の手順を使う。CI待ちだけでDraftに留めず、未採用案は勝手にReadyにしない。失敗・待機・権限拒否・成否不明も同スキルの手順で扱う。

## 5. マージし次のタスクへ進む

pr-to-mergeの依存順・マージ直前確認・main反映照合・関連Issue更新・必要な公開確認まで行う。ユーザーの「PRまで」等の終点を越えない。今回のタスクが完了したら、依頼範囲の次の着手可能タスクへ戻る。依存待ち・判断待ち・明示保留だけが残ったら、その条件を保存して終了する。新しい作業範囲を勝手に取り込まない。

自分の未commit・未pushを確認し、AGENTS.mdの終了形式で完了と残件を短く報告する。

```text
MERGED: #PR / PENDING: #PR(具体的理由・再開条件) / ISSUES: #Issue(完了・残件) / BRANCH: branch / NEXT: 次の1手
```

## 呼び出し例

- 「issue-to-mergeで、#123の残件をタスクにして実装からマージまで進めて」
- 「この親Issueの承認済みで着手できるものを、小さいPRにして順に完了して」
- 「このIssueの続き。既存PRと重複しないタスクから進めて。今回はPRまで」

スキル変更後の確認には [シナリオ](references/scenarios.md) を使う。実案件の現在状態・承認としては使わない。
