# Issueから実装・PR・マージまで

対象Issueの残件を確かめ、小さなタスクを一つずつ実装して完了まで進める。計画を出すだけで終えず、現在の依頼・権限の範囲で実行する。

## 正本・既存スキルとの分担

- 最初に対象refの [AGENTS.md](../../../AGENTS.md) と [現行資料ガイド](../../../docs/current_documentation_guide.md) を読む。Git安全、通信量、保存、CI・マージ条件はAGENTS.mdを正本とし、このスキルで上書きしない。
- 要望の解釈・台帳更新・横断確認は [owner-request](../owner-request/SKILL.md)、検証の選択は [web-build-test](../web-build-test/SKILL.md) を使う。台詞・画像等の実装には該当専門スキルを使う。本スキルはタスク間とIssue→PR→マージの進行を補う。
- 最新のユーザー指示と、この依頼に適用できる取得済み承認を確認する。過去の許可・採用判断を他のIssue、素材、操作へ一般化しない。スキルの呼び出しだけで保留解除や新たな公開範囲の許可を得たことにしない。依頼済みの作業を再承認させない。
- 「分解だけ」「PRまで」「これはマージしない」等の指定を終点として守る。実装依頼を全Issueの整理や仕組み作りへ広げない。

## 1. 現在地と着手可能な残件を確認する

1. リポジトリ、最新mainのSHA、作業branch/HEAD、作業ツリーを確認する。checkoutではAGENTS.mdのGit Safetyを実行し、他担当の変更を上書きしない。既存checkoutを再利用し、新規作業は最新mainから、保存済みPRの続きは既存branchで行う。
2. 対象Issueの本文・最新コメント・関連Issue・関連PR（open/merged/closed）と、対応する現行コード・正本の必要箇所を照合する。チェック欄、タイトル、古い引き継ぎだけで未実装・採用済みと判断しない。mergedとclosed未マージを区別する。
3. 残件を「着手可／既存PRで作業中／依存待ち／判断・採用待ち／明示保留／実装済み」に分け、根拠のコメント・PR・コードを添える。調査・提案・候補保存を実装承認とみなさず、保留は最新の明示指示で解除された範囲だけ進める。aiラベルや古い担当案を予約とみなさない。
4. 開いている関連PRの変更ファイルを確認する。同じファイルを変える未マージPRがあれば、既存branchで続ける、完了を待つ、独立タスクを選ぶ。Issue予約・claim・worker台帳は作らず、取得・解放も確認しない。
5. mainの最新CI・夜間検査の状況を確認する。未解消の失敗はAGENTS.mdに従い優先する。古いHEADの失敗、再実行で解消済みの失敗は現在の停止理由にしない。

Issue指定がなければ、依頼範囲の着手可の残件から、依存がなく小さく完了できるものを選び理由を短く示す。全件の棚卸し完了を着手条件にしない。関連履歴を取得できなければ未確認と明記し、それに依存する判断を推測で通さない。

## 2. 小さなタスクに分ける

大きなIssueは半日程度で実装・検証できる単位に分ける。各タスクを次の形にし、最初に実行するものを示してそのまま着手する。

| タスク | 完了条件 | 主な変更先 | 依存・重複 | 検証 | 対応PR・状態 |
|---|---|---|---|---|---|
| プレイヤーに起きる変化を1件で記す | どの操作・場面で何が成立するか | 実在する正本のパス | 必要な先行タスク/PR、なければなし | 局所再現と必要な回帰 | 既存PRまたは未着手 |

- 手段だけの「コード修正」「テスト」ではなく、単独で完了を判定できる変更にする。保存・進行・共通処理を触るものは境界条件も完了条件へ入れる。
- 既存子Issueやチェックリストを再利用し、分割しただけで子Issueを大量作成しない。小さな分解はIssue/PR本文で十分。独立して追う必要がある場合だけ子Issueを作り親へリンクする。
- タスク表は作業中の会話と既存Issue/PRへ置く。新しい予約制度、進捗bot、スナップショットMD、必須preflightを追加しない。
- 結果を大きく変える曖昧さだけ確認し、その部分だけ保留する。採用待ちの案を自分で決めず、独立して実行できる承認済みタスクを続ける。

## 3. 実装・局所検証を行う

1. 選んだタスクと関連正本だけを変更し、owner-requestの台帳・横断確認を行う。台帳の状態は実装済み、検証待ち、マージ済みを混同せず、未完を残す。
2. web-build-testと [remake/README.md](../../../remake/README.md) から変更・危険度に合う検証を選ぶ。局所再現→必要な関連回帰の順に確認し、全章通しを毎回要求しない。データには関連リンタを使う。
3. 各結果に対象HEADまたは未コミット差分、コマンド・対象場面、成功/失敗/timeout/cancel/未実施を記録する。同じHEADの成功は再利用し、無関係な変更で過去の局所検証を無効にしない。影響する実装・競合解消を行った場合は必要箇所を再検証する。正式な現HEADのCI条件とは分ける。
4. 差分をレビューし、目的外の変更、判定の緩和、未完の完了扱いがないことを確認する。Git Safetyを再確認して区切りごとにcommit/pushする。未完はDraft PRで保存する。

## 4. PRを作成しレビュー・CIを完了する

PR本文には「何がどう変わるか／Issueと今回完了するタスク／検証と対象HEAD／依存PR・残件・次の一手」を記す。全件を満たす場合だけ `Closes #番号` を使う。一部対応なら `Refs #番号` と完了項目・残件を記し、親Issueを閉じない。

- 既存PRがあれば同じPRを更新する。完成したらReady for reviewにし、CI待ちだけを理由にDraftへ留めない。採用待ち・未完成のDraftをCI目的で勝手にReadyにしない。
- 現行workflowと必須checkを確認する。現行は `.github/workflows/ci.yml` の `CI / result`。Draftではbrowserが省略されるので、Draft時代の緑だけで完成したPRの検証済みとしない。Ready後の実行で現HEADと必要なbrowser計画を確認する。
- PRコメント・レビュー・未解決スレッドを読み、実際の指摘に対応する。古いレビューが変更後も適用できるかを判断し、現HEADで必要な確認を残す。必要な承認や未解決の指摘を自作の承認・形式的な解決で置き換えない。
- CIが失敗したら現HEAD・失敗箇所を確認し、実装の不具合と環境要因を分けて修正する。必須checkの省略やassertionの弱体化で緑にしない。pushは修正をまとめて行う。
- CI待ちだけなら対象PR・HEAD・残る必須checkを一度記録する。短間隔の照会と同じ報告を繰り返さず、独立した有益な作業を進める。継続が難しい場合は保留理由と再開条件を保存し、未依頼の監視タスクを作らない。

## 5. 依存順にマージし完了を照合する

1. マージ直前に、最新指示・明示保留、PRのbase/head SHA、Draft状態、競合、必須CI、未解決の指摘と必要な承認を再確認する。現時点の権限で条件を満たす場合は速やかにマージする。
2. 積み重ねPRは先行PRを完了してからmainへbaseを変更する。依存PRがあるまま、そのbranch宛てにマージして「main反映済み」にしない。base変更・必要な競合解消後は差分とCI対象を再確認し、先行PRの古い緑を流用しない。mainに遅れているだけなら毎回取り込まない。
3. 可能な経路では確認したhead SHAをマージ条件へ指定し、確認後のpushとの競合を防ぐ。HEADが変わったら新しい差分・CIを確認して判断し直す。ブランチ保護や承認をadmin/bypass/forceで回避しない。
4. マージ操作の応答だけで完了とせず、PRのmerged状態・merge commitとmainへの反映を照合する。通信切断等で成否不明なら、再実行前に状態を読む。
5. 完了したタスクを根拠のPR/SHA付きでIssueに反映し、残件・保留があればIssueを残す。全完了時のみ閉じる。公開対象の変更なら既存deploy workflowの結果と対象SHAを確認し、マージ済みと公開済みを分ける。公開待ちを理由に完了済み実装を再実装しない。
6. 自分の未commit・未pushがないか確認し、AGENTS.mdの終了形式で短く報告する。

```text
MERGED: #PR / PENDING: #PR(具体的理由・再開条件) / ISSUES: #Issue(完了・残件) / BRANCH: branch / NEXT: 次の1手
```

権限拒否・通信制限は別アカウントや別経路で迂回しない。拒否された操作、対象、理由、完了済み範囲、未実行/成否不明を明記して該当操作だけ止め、独立作業を続ける。

## 呼び出し例

- 「issue-to-mergeで、#123の残件をタスクにして実装からマージまで進めて」
- 「この親Issueの承認済みで着手できるものを、小さいPRにして順に完了して」
- 「このIssueの続き。既存PRと重複しないタスクから進めて。今回はPRまで」

スキル変更後の確認には [シナリオ](references/scenarios.md) を使う。実案件の現在状態・承認としては使わない。
