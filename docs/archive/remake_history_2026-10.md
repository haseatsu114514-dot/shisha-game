## 作り直しの方針（旧版との違い・2026-10-07に旧 `web/` 削除済みの履歴）

| 観点 | 旧版 `web/` | リメイク版 `remake/` |
|---|---|---|
| コード構成 | `game.js` 1ファイル約9,000行（512KB） | 責務ごとのESモジュール（1ファイル数百行まで） |
| データ | `build_data.py` で `data.js` に束ねる（要ビルド） | `data/*.json` を**実行時に直接読む**（台詞の正本は共有＝二重管理なし） |
| 進行の書き方 | コールバックの入れ子 | `async/await` で章の台本を上から読める形に |
| セーブ | 継ぎ足しの互換コード多数 | スキーマ版数つき `state` ＋ `migrate()` 1か所 |
| 大会 | 既存工程に仕様を後付け | `docs/master_spec.md` 第2部（穴あけ/炭焼き/調整2回/10カウント）を**最初から**設計の軸に |
| 画面 | 固定16:9 | 固定16:9（1280×720論理座標）＋煙ワイプ遷移を共通化 |
| 見た目 | 墨×金＋LINE風スマホ＋看板型マップピン | **日常パートは旧版のデザインを踏襲**（オーナー指摘で揃えた・下記）。大会は紫／真鍮／銀の制作UIに統一 |
| 書体 | 端末任せ（明朝・ゴシック・ドット等が混在） | **Zen Kaku Gothic New の1書体に統一**して同梱（`remake/fonts/`・SIL OFL）。外部フォントは読まない |

日常パートの見た目は旧版と同じ語彙に揃えている（「スマホとアイコンのセンスが悪くなった」の指摘を受けて）。
別の見た目を足すときもこの語彙から外さない:

- **HUD**: 左上に墨×金の DAY カード（角飾り）、右上に体力・★段階の五角形・アプリ風の LIME・MENU（`daily/hud.js`）
- **マップ**: 街マップ `bg_osu_map_day/night` ＋看板型ピン（テーマ色・白縁・しっぽ・面識のある相手は顔ドット絵）＋右下の墨×金パネル（`daily/map.js`）
- **LIME**: ノッチ付きの端末・緑のヘッダー・白と黄緑の吹き出し・明るい返信欄の丸ボタン（`daily/phone.js`）
- **報酬通知**: ステ色（`--stat-*`）の漢字バッジのカード／好感度は顔ドット絵＋ハート（`core/ui.js` の `gainCard`）
- 顔アイコンは `assets/ui/face_icons/`（48px ドット絵）。`assets/ui/ui_*.png` は仮の色板なので使わない
- 外側の窓はラウンジの金縁を使い、窓の中のタブ・操作ボタン・小さな札は `css/ui-inner.css` の墨色と細い真鍮色の線で揃える。短い操作の文字は中央、説明付きの行動は左端を揃える。ステータスの情報・説明はグラフと5項目の下にまとめ、ショップはDAYカードの下から表示する
- 外側の会話枠・選択肢・HUD・パネル、地図看板・ハート・ゲージ・好感度の通知は `assets/ui/lounge/` の生成画像を使う。実行時用の7枚は `python3 remake/tools/build_ui_skin.py` で `remake/img/ui/lounge/` に作る。プロンプトは `docs/prompts/ui_lounge_prompts.md`。通知ウィンドウは項目別、地図の看板は場所の役割別の色を使う
- 日付・所持金のHUDは300pxの固定幅。体力欄は最大体力に合わせてゲージと外枠が一緒に伸びる（残量が減っても器の幅は維持）。所持金は上限999,999円で、HUDはその桁数に合わせた20pxの文字。日常はDAY1〜13、大会はDAY14で、HUDと台詞の残り日数は同じ大会日を参照する。体力ゲージは最大値に対する残量が50%超=緑、25%超〜50%=黄、25%以下=赤。好感度・絆の通知は同じ相手への連続加算を700msで一枚にまとめ、実際の点数と端数は加算時にそのまま反映する
- 大会当日のカウントダウンも「次の大会まであと0日」。スロット横のエリア名・時間欄と筐体下の名前プレートは出さない
- 地図は墨色の共通面と銀の縁に、能力の色と被らない役割別の差し色（キャラの店=スチール／家・拠点=アイボリー／その他=石墨／ショップ=茶系／大会会場=銀白）。能力バッジは読みやすい角ゴシックの「技・感・根・魅・察」を項目色の控えめな四角い枠に重ね、正式名を併記する（アイコン案と比較してオーナーが選択）。洞察は青緑、体力回復は黄緑で区別し、能力アップ通知は実際の増加量を `+NP` で表示。能力アップの各色の面には煙マークを付けない。通知からHUDグラフの対応する頂点へ色の光を運ぶ（動きを減らす設定では光の移動を省略）
- **書体**: すべて `var(--font)`（Zen Kaku Gothic New・太さ 500/700/900）。別の書体を足さない。
  収録文字は JIS 第2水準まで＋データ中の全文字。見慣れない字が豆腐になったら `python3 remake/tools/build_font.py <元TTFのフォルダ>` で作り直す

正史・仕様の正本は変わらない（`docs/gameplay_agent_reference.md` / `docs/master_spec.md` / `brand/story_and_structure.md` / `data/*.json`）。
リメイク版はそれを読むだけで、既存の台詞や設定を書き換えない。
リメイク版の進行だけで使う短い場面（チュートリアルの前後・リハーサル・通い訪問の小会話など）は
`data/dialogue/remake_ch1.json` に置いてある（他の台詞と同じスキーマ・同じリンタで検査される。旧版は読まない）。

### 台詞生成後の自然改行チェック（変更行のみ）

AI生成 → 変更した `text` / `inner` の抽出 → 本編・エディタ共通の
`js/vn/layout.js` / `text.js` で組版 → 診断と表示確認 → 必要箇所だけ修正、の順に確認します。
プロンプトだけで自然改行を保証せず、一括固定改行や意味の書換えで検査を通しません。

```sh
node tools/check_changed_dialogue_layout.mjs --base old.json --current new.json --output work/wrap-check
# または変更済みレコードだけの配列を渡す（形式: remake/test/natural_wrap_cases.json）
node tools/check_changed_dialogue_layout.mjs --records changed-records.json --output work/wrap-check
node remake/test/text_wrap.mjs --fixed-only
node remake/test/natural_wrap.mjs
node remake/test/browser/natural_wrap.mjs
```

既存のPlaywrightとChromeを利用できます。`PLAYWRIGHT_MODULE` は既存モジュールの絶対パス、
`CHROME_EXECUTABLE_PATH` はブラウザのパスです。検査は指定ファイルだけを読み、全台詞を探索しません。
base/currentはdialogue_idとJSON pointerで照合し、本文・本心・話者・種別が同じレコードを除きます。
配列の並べ替えは変更として扱うことがあります。削除レコードには描画対象がありません。

実フォントの通常998px・狭幅520px・本心併記700pxを、独立した共有組版ハーネスで確認します。
base/vn/ui-art/ui-innerの本番CSSとフォントを使い、1280×720ステージを844×390へ縮小します。
パネル画像だけは取得せず無効化し、枠・余白の寸法は本番CSSを保ちます。
通常・モバイルの本文は自然な998px、520pxと700pxはsyntheticWidth付き合成条件です。
viewport・ステージ・枠の収容とスクリーンショット寸法を検査します（ゲーム全体の起動・実機検証ではありません）。
本心併記モードでは本心がないレコードにも検査用本心を付け、その結果をsyntheticInnerで区別します。
本心は本編と同じplayerInner条件を適用します。外部通信は遮断し、新しいブラウザコンテキストを使います。
results.jsonには安定したfile/id/path、ページ、前後行付き分断診断、幅、フォント読込、画像名を保存します。
画像は各レコード・幅の最初のページ、幅超過は全ページを検査します。
疑わしい分断は人が確認し、フォント未読込・幅超過・ブラウザエラーは失敗とします。

組版はIntlの語とBudouXを併用し、「語＋の＋語」の連鎖を保守的に保護します。
まとまり自体が幅を超えるときだけ語境界、次いで書記素境界への分割を許します。
極小幅で禁則・単一書記素が収まらない場合も前進し、診断に残します。
Intlは品詞解析ではなく、同音・固有名詞・慣用句の意味の自然さを完全保証しません。
手動改行は固定で、この診断の自動修正対象ではありません。
反復DPは各開始位置の後続結果を保存し、幅に収まる候補までしか調べません。
通常24単位では約48書記素＋タグまでを先読みし、候補評価O(NW)、保存O(N+W)です
（Nはトークン数、Wは一行内候補数）。文字列連結・実測には文字列長に応じたコストが加わります。
極端に大きい指定上限・タグ列では候補評価も最悪O(N²)になるため、任意長入力の定時間保証ではありません。
