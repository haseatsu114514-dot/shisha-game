## 0. 結論（先に要点）

- **推奨置換先**: 第1章 **DAY7「中間準備」（`_ev_midcheck`）の「調整だけ」練習部分**を、なる戦（通常操作の通し制作＋スミの比較講評）に置き換える。
  - これは #1081 **E05「DAY7の調整だけ練習は不自然 → 普段の制作パートへ調整を統合」**を同時に満たす。なる戦は `pull`＋`care1/care2` を含む通し制作なので、「調整単独」を「通し制作の中の調整」へ自然に戻せる。
  - DAY7イベントにぶら下がる **仕入れ（`prepareFlavorStock`）・家シーシャ譲渡（`giveSumiRig`）はそのまま温存**し、入れ替えるのは中間の練習一台だけ。影響面が小さい。
- **判定方式**: 勝ち／負け／引分けを固定で付けず、**スミが軸ごと（配合・熱管理・提供状態）に二人の違いを述べる比較講評中心**を推奨。各軸の優劣分岐は**プレイヤーの実測値**（`cs.mixInfo.score`／`cs.heat.score`／`computeShisha(cs)`／提供温度）で決め、なるは固定の「堅い基礎」ベースラインを持つ。出来レースにならず、仲間意識と負けたくない気持ちを両立し、第2章の決裂を前倒ししない。
- **最大の設計論点（要オーナー判断）**: 必須制作である本イベントの時点で、**なるとの「面識」が未成立の可能性**がある（なる初対面＝KEMURIKUSA訪問は任意、全員の正式紹介＝DAY9「出場者説明会」）。誘い「今度スミさんに見てもらおうぜ」は既知前提の台詞なので、面識の担保方法を決める必要がある（→ §8 質問1・2）。

## 1. 第1章の必須（強制）制作の棚卸し

- #2 DAY3は「調整なし通し」、#3 DAY7は「調整だけ」、#4 DAY13は「通し＋調整」。段階学習として設計されているが、#3の「調整だけ」が E05 で「不自然」と指摘されている。

## 2. 置き換え候補の比較（2〜3案）

単純追加（必須制作を1回増やす）は Issue が禁止しているため除外。既存の必須制作1回の置換で比較する。

### 案A（推奨）: DAY7「中間準備」の調整単独練習を置換

- **内容**: `midPreparation()` の `runCarePractice()`（調整だけ）部分を、なる戦（通し制作＝`runFullPractice({adjustments:true})` 相当）に置換。仕入れ・家シーシャ譲渡は節として残す。
- **理由 / 相乗効果**:
  - #1081 **E05** を同時解決。「調整だけ」の不自然さを「通し制作に調整を統合」で解消でき、E の工程統一方針と一直線。
  - 通し制作なので操作は通常どおり（二台操作なし）。なるの一台は既存の実況演出（`broadcast` の `tickerSay`）＋短い台詞で並行表示でき、Issue の「はじめは通常操作／なるは既存演出で並行」に合致。
  - DAY14まで約1週間あり、「負けたくない」を育てても第2章の決裂（DAY後〜ch2）を前倒ししない余裕がある。
- **影響**:
  - 日程: DAY7の夜は既に tonari で、仕入れ・卓上台受領と同居。審査者スミは tonari の店長なので、審査の場として自然。
  - #1081 **B（日程・バイト・解放）**: B01〜B10 は主に DAY2 まわりとバイト動線の再設計。DAY7夜イベントの器（`NIGHT_EVENTS[7]`）は維持されるため、Bの日程変更と衝突しにくい（本イベントは Bの後で接続）。
  - #1081 **E（工程・調整）**: E03（練習/本番の工程・UI統一）、E06（調整は炭交換中心）、E07（葉の持ち引継ぎ）と工程を揃える前提で作る。E05はこの案で解消。
  - **DAY7 E05の調整単独練習**: まさにこの練習を置き換える＝E05の実体。
  - #1072（実制作評価）／#1073（バイト反応）／#1074（初回提供の素直さ）: #1072 の `served-eval.js`（PR #1102）で導入された「実配合＋提供温度の一言」を、本イベントのスミ講評の判定ロジックに**再利用**できる（§5）。#1074（初回提供の喜び）と口調トーンを揃える。
  - 面識論点（§0・§8）: DAY7時点でなる面識が未成立なら誘いが成立しない。要対応。
- **リスク**: 仕入れ・家シーシャ譲渡という既存の重要処理と同じ夜に同居するため、順序・SAVE境界の設計を丁寧に（§7）。面識未成立時のフォールバックが必要。

### 案B: DAY13「大会前夜」のリハーサルを置換

- **内容**: `rehearsal()`（本番と同じ通し＋2調整）をなる戦に置換。
- **理由**: 面識は DAY9「出場者説明会」で確実に成立済み＝誘いが自然に成立する。
- **影響・リスク**:
  - 前夜は本番直前の最終調整・緊張感の場。ここをライバル勝負にすると「本番の前夜に勝負した」＝本大会・本番との混同リスクが高く、Issue が禁じる「本大会後の回収や『勝った方が作る』約束との混同」を誘発しやすい。
  - 第2章の決裂を前倒ししやすい（前夜に負けを強く描くと、翌日の本番と章末の関係性に過剰干渉）。
  - リハの「本番想定の最終確認」という役割が消える。
- **評価**: 面識は楽だが、本番混同・決裂前倒しのリスクが大きく**非推奨**。

### 案C: DAY3「基礎の確認」を置換

- **内容**: `earlyPractice()`（調整なし通し）をなる戦に置換。
- **理由・リスク**:
  - DAY3はまだ基礎習得直後。ライバルと勝負するには早く、「負けたくない」を描くと理不尽（基礎未習で勝負させられる）。
  - なる初対面（KEMURIKUSA任意訪問）が DAY3までに成立している保証がさらに薄い。
  - 調整を含まない段階なので、スミの「提供状態・熱管理」講評の材料が弱い。
- **評価**: 早すぎる・材料不足で**非推奨**。

## 3. 推奨案（案A）の全体構成

DAY7夜 tonari。既存の `midPreparation()` の流れを次のように組み替える（仕入れ・卓上台は温存）。

1. **導入（intro）**: `remake_midcheck_intro` 相当をなる戦の文脈に差し替え。なるから「今度スミさんに見てもらおうぜ」の誘いが既に成立している前提で、スミの店（tonari）で勝負する段取りを置く。
2. **二人の狙い**: はじめ＝「仲間として見てもらいたい／でも負けたくない」、なる＝「強い相手と張り合いたい（`ch1_naru_first` の性分に接続）」。短く。
3. **仕入れ**: `prepareFlavorStock()` は維持（本番材料の確保）。順序はオーナー質問6で確定（勝負の前が自然）。
4. **共通制作工程**: `runFullPractice({ adjustments:true, coached:false, kind:"naru_match" })` 相当の通し制作。
   - はじめは**通常操作**（`setup→…→pull→care1→care2`）。
   - なるの一台は**既存の実況演出＋短い台詞で並行表示**（`broadcast` の `tickerSay`／工程の節目になる1〜2行）。**二台操作は要求しない**。なるの進行は演出のみで、プレイヤーの操作量を増やさない。
5. **スミの比較講評**: 実配合・熱管理・提供状態に連動する分岐（§4の表）。軸ごとに二人の違いを短く。
6. **なるの反応**: 負けん気と敬意の両立。第2章の決裂には踏み込まない（「次は負けねえ」程度に留める）。
7. **次の本編へ**: 家シーシャ譲渡（`giveSumiRig`）を経て、通常の DAY8 以降へ。

台本草稿は §6。

## 4. 判定方式の設計（勝敗 vs 比較講評）

### 4-1. 2案の比較

| 案 | メリット | リスク |
|---|---|---|
| **(α) 勝ち／負け／引分けを付ける** | 勝負として分かりやすい。負けん気の動機づけが強い。 | 固定勝敗は Issue が禁止。実測で勝敗を出すと、基礎が弱い序盤プレイヤーが「必ず負け」になりがち＝理不尽。報酬/罰則を付けたくなり未決事項に抵触。第2章の決裂の前倒しに繋がりやすい。 |
| **(β) 比較講評中心（軸ごとの優劣）＜推奨＞** | 固定勝敗を付けずに済む。軸ごとにプレイヤーの実測を反映でき出来レースにならない。仲間意識と負けん気を両立しやすい。報酬/罰則を保留できる。 | 「勝った/負けた」の明快さは弱まる（なるの台詞で負けん気を補う）。 |

→ **(β) 比較講評中心を推奨**。スミが軸ごとに「ここはなる、ここははじめ」と述べ、総合勝敗は断定しない。なるの反応で負けん気を表現。

### 4-2. 出来レースにならない判定（既存の採点値を使う）

なるの一台はプレイヤーが操作しないため、**なるは固定ベースライン**（entrance note「基礎が異常に堅い」＝崩れないが香りの冒険は控えめ、を数値化した定数）を持つ。講評の各軸は**はじめの実測値となるのベースラインの比較**で分岐する。実測は既存の値のみを読む（新しい品質を捏造しない）。

| 審査軸 | はじめ側の実測ソース（既存） | なるのベースライン（定数・案） | 講評の分岐 |
|---|---|---|---|
| 配合（ミックス） | `cs.mixInfo.score`（`stepMix`の採点） | 中〜高（例: 78。堅実だが冒険は控えめ） | はじめが上回る→「香りの冒険ははじめ」／同等→「どちらも筋がいい」／下回る→「組み立てはなるが一枚上」 |
| 熱管理・炭 | `cs.heat.score`（`runHeat`） | 高（例: 85。堅い基礎の核） | 下回る→「熱の芯はなる」／同等以上→「熱も詰めてきたな」 |
| 提供状態 | 提供温度 `cs.pull.temp` を `temperatureBands(cs)`／`isIdealTemperature` で判定（PR #1102 の `servedStateLine` ロジックを再利用） | 「良好帯」固定 | はじめが良好帯→「提供はどちらも落ち着いている」／高い→「熱が前へ出た」／低い→「香りがまだ遠い」 |
| 完成度（任意） | `computeShisha(cs).craftQuality`／`.aroma` | 中〜高 | 総合は断定せず、締めの一言に使う |
| 調整 | `cs.care.score`（`runCare`） | 中（例: 72） | 上回る→「立て直しははじめ」 |

- **再利用**: 提供状態の講評は PR #1102（#1072）の `remake/js/craft/served-eval.js`（`servedTasteLine`/`servedStateLine`/`temperatureBands`/`isIdealTemperature`）をそのまま流用できる。はじめの「一口の感想」をスミの比較講評へ横展開する形。新規の採点系を作らない。
- **本大会の審査員・票配分は変更しない**（Issue明記）。本イベントはスミ1人の講評で、`showStandings`／`resultTable`／南雲の票などの本番審査系には触れない。
- なるのベースライン定数は**台本側に講評テキストとして持たせる**のが安全（スコア定数を新設すると #1081 F/G の報酬境界に波及しうる）。実装時に定数の置き場所をオーナー/Sol と確認。

## 5. 並行表示（なるの一台を操作させずに見せる）

- プレイヤーは自分の一台を通常操作。なるの進行は **`remake/js/craft/broadcast.js` の既存 `tickerSay`** と、工程の節目に差し込む短いなる台詞（1〜2行）で見せる。

  - `stepMix` 後: ticker「なるは菓子の後味から逆算して葉を選んでいるようだ」。
  - `runHeat`〜`stepSteamTime`: なる「立ち上がりの3分は我慢だ（独り言）」（`ch1_naru_first` の口癖に接続）。
  - `runPull`（提供）: なる「……っし、出した」。

## 7. 状態設計（フラグ・SAVE/LOAD・中断・繰り返し防止）

### 7-1. フラグ構成（既存 `earlyPractice`/`midPreparation` パターンに準拠）

- 完了キー: `_ev_naru_match`（`NIGHT_EVENTS` の `once`/`doneKeys` と同じ粒度。done()=`flag("_ev_naru_match")`）。
- 進行オブジェクト: `state.flags._ch1_naru_match = { introRead, stockDone, practiceDone, feedbackRead, result }`。
  - `midPreparation()` が `stockDone`／`practiceDone`／`feedbackRead` を段階保存するのと同じ構造にし、各段の直後に `save()`。
  - `practiceDone` は**実制作が提供まで到達したときだけ**立てる（`runFullPractice` が `pullDone` 無しで中断すると throw する既存挙動＝`earlyPractice` の `cs.pullDone` ガードを踏襲）。
  - `result` は §4 の軸ごと判定の**スナップショット**（例: `{ heat:"hajime"|"naru"|"even", mix:..., served:"ideal"|"hot"|"cold" }`）を保存。LOAD後の講評再表示で実測を取り直さず、保存済みresultで同じ分岐を出す（二重採点防止）。

### 7-2. SAVE/LOAD・AUTO/SKIP・中断再入

- **中断再入の二重処理防止**: `earlyPractice()` の `WeakMap`＋`requireCurrent()`（owner/chapter/day/slot/phase一致）パターンをそのまま流用。別stateへLOADした場合は旧taskを使わない。
- **一台の作り直し防止**: `feedbackRead` が立っていれば同じ一台を作り直さない（`earlyPractice` の `if (!progress.feedbackRead)` と同じ）。
- **仕入れ・家シーシャの一度性**: `prepareFlavorStock()` は `stockDone` でガード、`giveSumiRig()` は既に「一度だけ・途中再開でも渡す」実装（`ch1.js:410`）。本イベントでも末尾で呼び、二重付与しない。
- **費用・報酬・材料**: 未決のため**最小版は無費用・無報酬**（VNの報酬キューも付けない）。将来付けるなら「分岐の外（共通処理）に一度だけ」置き、SKIP/LOADで二重付与しないこと（交流の時系列ルール §3・報酬キュー規約）。
- **AUTO/SKIP**: 並行表示の ticker・なる台詞は通常のVN行として扱い、SKIP に追従。提供状態の講評で温度カメラ等の演出を足す場合は、PR #1101 の `skipMode`／`reducedMotion()` ガードに倣う。

### 7-3. 繰り返し防止（交流の時系列ルール §交流の時系列ルール 準拠）

- **大会後・第2章で誘いを繰り返さない**:
  - 事前の誘い（§6(1)）を出す経路（LIMEまたはKEMURIKUSA来店）は `flag("_ev_naru_match")` 成立後は出さない。
  - 本大会後に「今度勝負しよう」「本番よろしく」等を言わないこと。該当台詞には共通VN条件 `condition_type:"tournament_finished"` / `tournament_chapter:1`（`next_true`=大会後 / `next_false`=大会前）を付け、大会後は「この前の稽古」の回顧へ置き換える。判定正本は `remake/js/core/story-context.js`。
  - 第2章の決裂（`naruRiftActive(state)`／`_ch2_naru_*` 系）と混同しない。本イベントは決裂を前倒ししないため、`naru` 戦の結果フラグを ch2 の決裂条件に流用しない。
- **「勝った方が作る」約束との区別**: 既存 `ch1_naru_promise`（優勝翌日・敗者の店で勝者の一台を作る）は本大会後の回収。本イベント（練習勝負）とは別物として、台本・フラグを分ける。

### 7-4. テスト計画

- 新規 Node テスト `remake/test/naru_match.mjs`（`tools/ci/suites.json` の quick へ1件追加。workflowは増やさない）:
  - 順序: 誘い→通し制作→講評→次本編 のトレース。
  - フラグ: `_ev_naru_match` / `_ch1_naru_match` の段階保存、`practiceDone` は `pullDone` 必須、LOAD再開で一台を作り直さない。
  - 二重処理なし: 仕入れ・（将来の）報酬・既読が中断/再入で増殖しない。resultスナップショットで講評が同じ分岐を再生。
  - 判定: 代表入力（heat高/低・提供ideal/hot/cold・mix冒険/素直）でスミ講評の分岐が実測に一致。固定勝敗を出さない。
- `remake/test/story_context.mjs`: 大会前/大会後/第2章で誘い台詞の分岐（`tournament_finished`）を追加検証。
- `remake/test/tournament_sequence.mjs`：本番審査系に触れていないこと（回帰）。
- 台詞 lint: `python3 tools/lint_dialogue.py ch1_naru`／`ch1_main`（新規行の話者ID・行長・報酬キュー・禁止語）。
- ブラウザ: 必要なら DAY7夜の実MENU SAVE/LOAD＋再入＋繰り返し防止の1本だけ（path選択）。全件は走らせない。
