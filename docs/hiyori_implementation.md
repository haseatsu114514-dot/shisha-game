# 泡沢ひより・実装基盤と台本の接続仕様

オーナー依頼による追加ヒロイン。初遭遇はtonari以外のシーシャ店で偶然話しかけたひよりが『どこかで働いてるの？』と問い、はじめがtonari勤務だと答えて初めて自分は元バイトの先輩だと明かす構成がオーナー指定。店名・日時・正式台本・本編への接続は未決のため、現段階では本編へ自動登場させない。長文シナリオはClaude制作予定。
キャラクターの正本は [`data/characters.json`](../data/characters.json) の `hiyori`。年齢・外見・職歴などの事実はそこだけで管理する。

## 現在できること

- 起動時にキャラ・表示確認用台本・未接続のルート定義を読む。名乗る前は既存仕様どおり「？？？」、名乗った後は「ひより」。
- 台詞行の `inner` を表の台詞の後に、小さめの淡いピンク・括弧付きで出す。クリック・Enter・Space・AUTO・SKIP・ログ・長文の改ページに対応。
- 本心は発話・報酬キュー・知識フラグ・演技の崩壊演出として処理しない。主人公が知るのは、表の言葉・表情・行動だけ。
- 既存の好感度、隠し恋愛値、恋人、友人、LIME、私的デートの形式に対応。短い恋人／友人の会話を追加済み。
- イベントを実際に読み終えた後に既存の `flags` と `story.hiyori` へ記録。再読・同時呼出しで二重に報酬を受け取らない。
- 専用ハガルと正式台本が揃うまで締めくくりと告白を起動しない。好感度MAXだけで告白しない。
- 人間関係の画面は面識を得た後だけひよりの行を出す。顔アイコン・立ち絵が無い間は画像URLを作らない。

[`remake/hiyori-preview.html`](../remake/hiyori-preview.html) は本番VNを使う別ページの試写。メモリ上の仮状態だけを使い、本編のセーブや設定を読み書きしない。
5本の短い例は正式な登場シナリオではない。斧投げの背景は未制作のため、他の店を斧投げバーとして代用せず暗い背景で表示する。

## 台詞形式

```json
{
  "speaker": "hiyori",
  "face": "sad",
  "text": "明日のことは、煙に預けて……",
  "inner": "交通費の申請二十件。煙では承認できない"
}
```

`inner` はひよりの通常台詞行だけに置く。他キャラ・制御行・本心だけの行には付けない。
括弧はUIが付ける。既に全角括弧で閉じた文字列も二重括弧にしない。HTMLはエスケープし、装飾タグは既存のものだけを使う。
手動改行なし、表の台詞は全角48字以内、本心も括弧込みで48字以内を目安にする。
長い本心は2行ごとにページを送り、各ページで括弧を閉じる。表の台詞が複数ページなら最後のページの後に本心を出す。
本心の続きのページでは、最後の表の台詞を残す。AUTOの待ち時間は両方の文字数を使い、本心には発話の文字送り音を付けない。
ログは1発言を1件にまとめ、下段に本心を別色で表示する。ログを開いている間は自動送りとキーボード送りを止める。

強弱を付け、全行に本心を付けない。元スタッフの知識、経費精算、通知、食べ物、斧投げ、好意を使った独自の状況を作る。
はじめの返事は、聞こえた言葉や見えた行動だけに対応させる。スミさんがすぐ正体を説明する構成にしない。
特定の動画の台詞・構成・固有のギャグは転用しない。
恋愛の見せ場は、普段は `inner` にあった「好き」「会いたい」「帰りたくない」が初めて `text` になる瞬間。その行に同じ内容の本心を重ねない。

## イベント・フラグ

接続条件の正本は [`data/dialogue/hiyori.json`](../data/dialogue/hiyori.json) の `route`。
`enabled: false` を初期値とし、登場日やマップへの入口はまだ追加していない。
`events[].dialogue` はこれから制作する台本の予約ID。未制作のIDを再生しようとしても、表示サンプルを正式台本の代用にしても発火しない。

| 段階 | 台本の予約ID | 読了フラグ | 条件の骨格 |
|---|---|---|---|
| 出会い | `hiyori_meeting` | `_hiyori_meeting_done` | 第1〜2章。他店でひよりが偶然『どこかで働いてるの？』と聞く→はじめがtonariと答える→元バイトの先輩と判明。店名・日付は未決 |
| 綻び | `hiyori_cracks` | `_hiyori_cracks_done` | 出会い読了、面識、好感度♥1以上 |
| 斧投げで正体発覚 | `hiyori_axe_reveal` | `_hiyori_real_self_known` | 綻び読了、面識 |
| 素顔と仕事 | `hiyori_work_talk` | `_hiyori_work_talk_done` | 正体発覚読了、面識、好感度♥2以上 |
| 東京からの連絡 | `hiyori_tokyo_contact` | `_hiyori_tokyo_contact_seen` | 第3章、仕事の話読了、連絡先あり |
| 本心が声になる | `hiyori_feelings_spoken` | `_hiyori_feelings_spoken` | 第3章まで、仕事の話読了、恋人の絆Lv2以上 |
| 海外大会への応援 | `hiyori_dubai_support` | `_hiyori_dubai_support_seen` | 第4章、仕事の話読了、連絡先あり。現地同行とは別 |
| 友人として継続 | `hiyori_ch5_friend` | `_hiyori_ch5_friend_seen` | 第5章、仕事の話読了、友情の着地済み |
| 恋人として継続 | `hiyori_ch5_lover` | `_hiyori_ch5_lover_seen` | 第5章、仕事の話読了、恋人 |

これらは順序と接続条件の基盤。好感度の数値、繰り返し交流、具体的な発火日、場所、消費行動数は登場設計と合わせて調整する。
正体が分かっても儚い演技は継続できる。プレイヤーが本心を見たことだけでは `_hiyori_real_self_known` を立てない。

名乗りの瞬間には既存形式の `{ "type": "set_flag", "flag": "_met_hiyori" }` を置く。
連絡先を実際に交換した箇所には `_lime_contact_hiyori` を立てる。後続の章へ移ってもこの面識・連絡先・関係・読了を保持する。
旧セーブの訪問回数や好感度から、これらの出来事を推測して埋めない。

## 既存の恋愛・友人システムとの接続

1. `hiyori_work_talk` の後に `hiyori_bond_question` を接続。選択肢は `id: "bond_q1_hiyori"`、`romance_char: "hiyori"`、各項目に `romance: 1` または `0`。
2. 好感度MAXかつ4本の物語を読了した後に `hiyori_bond_finale`。恋愛が開いているかは既存の `condition_type: "romance_open"`、`char_id: "hiyori"` で分岐する。
3. 締めくくりの最後の選択肢は `bond_q2_hiyori`。途中の質問を実際に回答済みであることも条件にする。専用ハガルは恋愛・友人のどちらにも渡す。ハガルは未決のため `route.finale.gift: null`。実在する `data/equipment.json` のIDを登録するまで締めくくりを無効にする。
4. 告白は既存形式の `confession_hiyori` から `confession_hiyori_accept`／`confession_hiyori_reject` へ `next_id` で分岐。共通 `onDialogueEnter` が恋人または友達の状態を記録する。途中の質問と最後の質問で恋愛を重ねた相手だけ予約する。
5. 恋人の絆は既存の私的デート・LIMEでだけ伸ばす。デートと友人の一服の文面にある `inner` も本番VNへ引き継ぐ。LIMEの文面は実際に送信した言葉なので、プレイヤー専用の本心を混ぜない。

ひよりにも既存の「はじめが想いを伝えるか決める」「既に恋人がいるときの確認」が使われる。
第1章の複数恋人の修羅場は既存3人の組合せ台本のみで、ひよりとの組合せは未制作。対応済みとして報告しない。

正式な入口からは [`daily/hiyori.js`](../remake/js/daily/hiyori.js) の `playHiyoriEvent(eventId)` を明示的に呼ぶ。
`availableHiyoriEvents()`／`hiyoriEventStatus()` は条件確認用。自動カレンダーは起動しない。
行動の体力・費用・日付・場所の移動は呼出し元の責任とし、実際に体力を使う自由行動なら既存の `paidAction` に包む。
締めくくりは既存の `finaleDue("hiyori")`／`playFinale("hiyori")` を使う。

### tonariの歴代アルバイトと「帰りたいのに帰れない」物語（オーナー追加確定・2026-10-11）

**人物の動機と、序盤〜中盤に守ること**

- **優秀だが仕事疲れは本物**。ひよりは25歳、社会人3年目の総務で仕事はできるエリート寄りの人物。責任感が強く、最近は業務の重圧と忙しさに本当に疲れている。病弱・怠惰・能力不足・壮絶な過去という理由へ変更せず、忙しい現実が再会一回で消えたことにもしない。
- **かなり遅咲きの厨二病**。本当に疲れた現実から逃避したい気持ち、悲劇のヒロインを気取りたい欲望が行き過ぎて、「私は儚い女だから」と全力で物憂げなお姉さんを演じる。25歳でアラサーを意識し、相手探しに焦っている。**『儚い女なら男性にモテる、守ってもらえるはず』という本人の考え**も芝居の原動力。焦りは彼女自身の内心であり、周囲が年齢で否定したり、恋人がいない価値のない人扱いしたりしない。演技を悪意ある詐欺にも深刻な精神疾患にも変えない。
- **以前の『最近アニメにハマって、儚い登場人物に憧れて演技を始めた』設定は撤回**。アニメを芝居の動機にしたり、特定の作品名を後付けしたりしない。『厨二病』は振る舞いの比喩。儚く見られたい欲求と、優秀で明るい本来の姿との落差が核。

### 憧れているのは『本物の儚さ』、自分は『儚い女ぶりたい』（オーナー追加決定）

- **性格の核**：『ちいかわ』のモモンガが『かわいく思われたい』と振る舞うように、ひよりは**『儚い女に見られたい』『儚いお姉さんぶりたい』**。参考にするのは承認欲求と、理想像を自分から大げさに演出する構図だけ。既存IPの台詞、口癖、見た目、具体的なエピソードは転用しない。ひより自身の性格・職歴・好きなもの・口調を守る。
- **自然体との対比**：つむぎは寡黙で物静か、ましろは眠そうでおっとりしており、どちらも**儚く見せようとはしていないのに、ひよりの目には自然に儚げに映る**。本人たちが自分を儚い女と認識していたり、病弱・不幸・悲劇的な人物だったりする設定にはしない。特にましろは第3章のmukai所属なので、ひよりとの出会いを第1章へ無理にねじ込まない。

- **頻度の最優先制約**：普通の会話は儚さの自己演出と内心の落差で成立させる。**本当の素が爆発して大声で叫ぶのは、ごくまれ**。台詞制作担当はギャグとして便利でも頻発させない。下にある叫びのラフは発生頻度の見本ではなく、もし発生するときの例示のみ。
