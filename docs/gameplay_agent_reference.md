- 1つのフォントファイルは1つの名前で登録する。基本＝`Suien Gothic`（500/700/900、`var(--font)` で使う）、会話の明朝＝`Suien Blue Mincho`（400）、名前札の明朝＝`Suien Name`（700）、制作画面の明朝＝`Craft Mincho`（700）、ドット体＝`Chapter Preview Dot`（400）、導入＝`Intro Gothic`。同じファイルを別名で登録し直さない。
- 通常のUI・数字・金額は `var(--font)`。`sans-serif` や Arial・`system-ui` を単独で指定しない。ほかの書体を使うときも `"<書体名>", var(--font)` のように基本書体を控えに置く。
- 登録していない太さを指定しない（ドット体と会話の明朝は400だけ、名前札と制作の明朝は700だけ）。合成の太字になる。
- 文字の大きさは、12px未満を読ませる文字に使わない。12〜13pxは太さ700以上・字間0.02emまで。
- **飾りは例外**: ゲームオーバー（コンティニュー）のネオン型カウントダウン数字（`continue-neon.css` の `.go-count`）と斧のメニュー表の見出し（`axe-menu.css` の `.axe-menu h1`）の Georgia は飾りとして残す。読ませる文字・数字・金額には使わない。
- `Craft Mincho` は Zen Old Mincho Bold から制作画面の文字だけを抜いた書体。`remake/js/craft/` に新しい漢字を足したら `python3 remake/tools/build_craft_font.py` で作り直す（ネット取得なし。足りない字は単語の途中で書体が割れる）。

### シーシャ屋の文化・共通ルール

以下はゲーム全体を通じて守るべきシーシャの文化的ルール:

- **ミントの好み**: ミントが苦手な客もいる。ただし**毎回口頭で確認はしない**（不自然なため）。苦手な客は注文時に自分から「ミント抜きで」と言う、常連は好みを店が覚えている、という形で描く。
- **蒸らし時間**: 2026-10-08のオーナー指定で、固定の選択肢から **キッチンタイマーの10秒単位の自由設定**へ変更。上限は10分、基本は5〜8分。10分は将来の特に熱を必要とする葉・機材向けで、通常はほぼ使わない。5分は吸い出しを低温から始め、8分ならじっくり熱が入る。0分（吸いながら立ち上げる）は神崎竜二との交友で解放する将来の高等テクとして残し、現行のタイマーは00:00では開始できない。
- **炭の配置**: 初期はフラットかキューブの **トライアングル（三角3個）**。配置を決めてから必要個数を焼く。`_coal_four_unlocked`／`_coal_mix_unlocked` で4点・混合を追加できるが、後続章の解放イベントは別作業。
- **お任せ注文**: 「お任せで」と頼む客は珍しくない。普通にある注文の仕方。
- **水と煙の説明（#1113 / #1128・K14）**: ボトルの水の役割は**「煙を冷やして吸いやすくする」だけ**と説明する。ニコチン・タールなど有害物質への影響は**「諸説ある」とし、濾過する・減らすと断定しない**。煙が濃く出る（爆煙）理由は水ではなく**「グリセリンと熱の仕事」**。正本の台詞は `data/dialogue/ch1_sumi.json`、図解は `remake/js/vn/shisha-diagram.js`。
- **用語の統一**: HMD（ヒートマネジメントデバイス。HMSと書かない）、タヌキッシュリッド（ターキッシュリッドと書かない）、ハガル（ボウル）、地の文・台詞は「煙」（用語集の「正確には蒸気」は豆知識としてのみ）。実在ブランド名（Al Fakher 等）は出さず、作中のパロディ名（アルファーヘブン・ドバジ・アフサール・フォースフェクタ・フワリ・ナイトサイド）を使う。
- **数値の精度**: チャコール博士の「炭の火入れ0.5秒」はキャラの持ちネタとして残す（K14・オーナー決定）。それ以外の「1ミリ」「1.2℃」のような実測めいた数値を地の文に増やす提案（`docs/reports/issue1107-*`）はオーナー未決定で、採用扱いにしない。シーシャ描写の参照先一覧は `docs/shisha_reference.md`。
- **吸い出し**: 炭を置いて蒸らした後、提供前に何度か吸って温度を立ち上げる工程（最低2回・3回までは無傷、それ以上は葉が痩せて減点。最大5回。やめ時は自分で選ぶ）。吸い方で熱を上げ下げできる。待機中の温度は安定させ、点線で「今止めたら到達する温度」を示す（2026-10-08 PF66）。少穴は待機中の振れではなく吸い方による温度変化を大きくする。
- **コンセプト選択とプレゼン／FLAVOR TRIALは廃止（2026-10-11 TP01・02）**。提供後に同じ一台を2回調整し、完成品を審査する。穴・炭・完成品・調整1・調整2を各20%で集計。制作・中間投票・審査結果は別々に示し、南雲の「最後の一票」が先頭のはじめに入って優勝を締める第1章の正史を維持する（#1282 以降、逆転ではない）。過去のtrial仕様を復活させない。
- **詰める量**: 基本12g。ボウル（ハガル）の容量までは増やせる（素焼き・大型は15〜20g）。多く詰むほど味の劣化は遅いが、必要な熱と葉代が増える。
- **ダブルアップルの味の正史（2026-07-20確定・絶対にブラさない）**: 林檎そのものの味ではなく、**アニスとリコリス──二つのスパイスの香りで林檎を再現した、シーシャにしかない独特な味**。独特だからこそシーシャ好きなら一口でそれと分かる。❌「林檎飴の甘さ」「果汁感」等、果実の林檎味としての描写は禁止。❌略記「DA」も禁止（必ず「ダブルアップル」と書く）。ch3のダブルアップル事件でましろが出すのは**グレープ**（アニスとリコリスの気配が一粒もない果実味。健康な舌なら間違えようがない二つの取り違えが、味覚喪失の動かぬ証拠になる。❌シトラスミント・シナモンは旧設定）。

## 現行版の開発ワークフロー

1. Git Safetyを確認し、最新 `origin/main` から作業ブランチを切る
2. 台詞は `data/dialogue/*.json`、画面・進行は `remake/` を編集
3. 台詞を触ったら `python3 tools/lint_dialogue.py`（ERROR=0）、`python3 tools/tidy_dialogue_text.py --dry-run`
4. **検証は変更した該当箇所を基本にする**（2026-10-09 オーナー指示・TEST01）。BGMなら再生・切替・音量、表示なら変更画面、ミニゲームなら変更工程だけを確認する。テストの候補は `.claude/skills/web-build-test/SKILL.md`。表にある全テストや通しテストを毎回実行しない
5. commit・作業ブランチへのpush・PR。mainへの直push・forceは禁止

ローカル確認: `python3 remake/tools/serve_preview.py --port 8123` → `http://127.0.0.1:8123/remake/`。
重いブラウザテストは直列で実行。PlaywrightのChrome指定はテスト冒頭または `remake/README.md` 参照。

通しテストは、全体の進行・セーブ互換への広い影響、局所確認では切り分けられない不具合、またはオーナーの明示依頼があるときだけ選ぶ。実行するなら必要な理由を短く伝える。同じ変更で確認済みなら、追加変更・失敗・未解決の懸念がない限り繰り返さない。複数チャットでの重複実行も避ける。

- 登場カットの名前は会話欄と同じ呼び名のみ。括弧付きの本名は全員で廃止し、本名はストーリーの名乗りで扱う（2026-10-08 CI48）。旧案の比較画像は修正前の状態で保存してよい。
- テスト用フックは `window.__remake`（`vnTest`・`craftTest`・`dev`）。維持する
- タイミング系は共通の `countdown()` で3・2・1を挟む
- 状態は `core/state.js` の単一 `state`、報酬は `core/stats.js`、会話は `vn/engine.js` の `play()`
- 残り日数は `daily/hud.js` の `daysLeft()` と `{daysLeft}`。台詞に直書きしない
- ステの今の合計値（0〜100）はUIに出さない。★・レーダー・抽象語で示し、通知の実増加量 `+NP` は表示する
- 台詞エディタは `python3 tools/text_editor_server.py`（現行の `vn/text.js` を配信）。JSONを保存後、本編を再読み込みすれば反映

## 矛盾・改行崩れの再発防止ルール（2026-06-15）

ストーリー矛盾・会話破綻・改行崩れは「設定が複数箇所に散って二重管理になっている」「改行がデータとコードの両方で決まる」「報酬がプロサ（地の文）に埋まっている」という**構造**から生まれる。以下を守ること。

### 交流の時系列ルール（必須）

全章の好感度・友情・恋愛・店舗訪問イベントに適用する。好感度や交流の何回目かは大会進行と独立している。新規制作・既存修正・未接続原稿の本番接続時には、遅れて同じ段階を読む場合も成立させること。

- 大会前を前提とする台詞・選択肢・地の文には、必ず大会後用の分岐を用意する。大会後は、その大会の参加登録・決意表明・対戦予告・「いよいよ」「本番よろしく」「明日の大会」等を話さず、現在の店の仕事や二人の交流に沿った会話へ置き換える。次の大会があると勝手に補わない。
- 共通VN条件 `condition_type: "tournament_finished"` と `tournament_chapter: N` を使う。対象大会は章番号Nで明示する。`next_true` が大会後、`next_false` が大会前。判定の正本は `remake/js/core/story-context.js`。対象章の `aftermath` / `cleared` と後続章で大会後になる。別の章の後日談を現在の大会の終了と混同しない。日数・好感度・訪問回数で終了を推測せず、新しい保存フラグを追加しない。
- 「その人物と初対面」「その店へ初入店」「初めて客として交流」は区別する。配達・偵察・強制の顔合わせ・大会紹介等で既に会っていれば、交流0回でも初対面の挨拶を繰り返さない。`met` / 実際の紹介・訪問の既存記録で分岐し、面識だけで好感度イベントを既読にしない。古い未訪問用原稿を、強制訪問がある現行ルートへそのまま接続しない。
- 時系列分岐の外に、共通の選択記録・思い出・成長・贈り物の処理を置き、どちらでも同じ一度性を保つ。台詞を短くした結果、報酬や既読を飛ばしたり二重付与したりしない。固定の大会前夜イベントは固定進行の条件を確認し、自由交流とは分けて扱う。
- 追加・変更したイベントは、同じ交流段階・好感度で「大会前／同章の大会後／後続章」を検証する。面識が関係する場合は「未対面／顔合わせ済みだが交流0回／訪問済み」も確認する。中断・SAVE/LOADで分岐が保存中の章・進行に追従し、報酬・既読が増殖しないことを確認する。未接続の原稿や `_legacy/` の台詞を現行の再現バグと断定しない。

```json
{
  "type": "condition",
  "condition_type": "tournament_finished",
  "tournament_chapter": 2,
  "next_true": "after_tournament",
  "next_false": "before_tournament"
}
```

分岐先は同じ会話の `branches` に書く。共通検証: `node remake/test/story_context.mjs`。台詞lintと、変更した実際の訪問経路の検証も行う。

### 1. 設定の一元管理（Single Source of Truth）

各「事実」には**正本を1つだけ**置く。他は参照するだけで、事実を書き直さない。

| 事実の種類 | 正本（ここだけを編集） | 二次（手で同期しない） |
|---|---|---|
| キャラのID・本名・年齢・ステータス | `data/characters.json` | brand/docs の人物表は説明用。数値・年齢を書かない |
| 表示名（あだ名）・話者の別名 | `data/characters.json` の `name` | ⚠️ `remake/js/core/data.js` の `displayName()` が正本を参照。名前をハードコードしない |
| ステータス名（5種） | docs/gameplay_agent_reference.md「ステータス」節 | コード定数 `STAT_KEYS`/`STAT_JA2EN`（engine.js）と一致必須 |
| 大会名・章レギュレーション | docs/gameplay_agent_reference.md「大会名・大会システム」節 | story_and_structure.md は説明、矛盾したら本資料が正 |
| 章ごとのストーリー（プロット） | `brand/story_and_structure.md` | docs/master_spec は仕様、brand のフィードバック系は履歴 |
| 台詞 | `data/dialogue/*.json` | 現行版は正本JSONを直接読み、複製・バンドルを作らない |

- 同じ事実を2箇所に書かない。書くなら一方を「→ ○○を参照」にする。
- ⚠️ **正本だが古い記述が残っている既知の地雷**:
  - brand/docs に**旧タイトル「煙の向こう側」「ケムリの向こう側」**が残ることがある。**正式タイトルは「水煙前線 -EN:CODE-」**（本資料が正）。見つけたら直す。
  - `brand/brand` / `brand/chapter1（character）` は**旧設定の残骸**（旧名「ドクター・ケムリ」、旧主人公表記「蒸野 はじめ」等）。**参照・引用しない**。`review_scope.md` の「コア」に `brand/**` とあるが、これらの旧ファイルは正史ではない。

### 2. 改行は「コード側（autoWrap）」に一本化する

改行は **`remake/js/vn/text.js` の `autoWrap()`（`WRAP_LIMIT=24` 全角換算・禁則処理つき）＋ 最大2行で改ページ（`MAX_PAGE_LINES`）** が決める。**データ側で決めるのではない**。

- 語の途中では折らない。句読点で折れない行は、手前の文節の頭で早めに折る（同梱の BudouX 日本語モデル `vn/budoux_ja.js`）。文末（。！？）優先は、それで改ページが増えない時だけ（2026-10-09 TX01）。検証は `remake/test/text_wrap.mjs`。

- 台詞テキストに**手動改行 `\n` を入れない**。手動 `\n` は autoWrap の前段で分割されるため、(a) 旧フォント幅向けの改行が残って二度折れする、(b) 短い断片が孤立する、(c) 改ページ位置がぶつかる、という崩れの主因になる。
  - 例外: 演出上どうしても改行したい箇所のみ。その場合も**1行が全角24文字を超えない**ように書く。
  - 既存の手動 `\n`（`lover_events.json` に多数）は崩れ報告が出たら撤去方向で直す。
- 1台詞は**全角24文字×2行＝48文字**を目安に収める。超えると自動で改ページされ、文の途中で切れて不自然になる。長い説明は台詞を分ける。文節で早めに折るため、40字台でも3行になることがある＝台詞エディタか `text_wrap.mjs` で確かめる。
- 一文を2つの吹き出しにまたがせない。心の声は各行を（）で閉じる（心の声の色は「（」で始まる行にだけ付く）。lint が閉じていない括弧をWARNする。
- 改行確認は台詞エディタ（`python3 tools/text_editor_server.py`）（現行の組版を直接配信）。句読点・改行の規範と自動整形は **text-style スキル**参照。日数は直書きせず `{daysLeft}`（`interpolate()`）を使う。

### 3. 報酬を地の文に埋めない（埋めるなら厳密に）

ステ上昇・好感度は `remake/js/vn/engine.js` の `parseCue()` が**台詞テキストを正規表現で読んで**発火する（`/(技術|センス|根性|魅力|洞察|好感度)/` ＋「上がった／少し上がった／かなり上がった／大きく上がった」）。これは台詞を書き換えると報酬が黙って壊れる／重複する温床。

- 報酬を確実にしたいイベントは、地の文頼みにせず `type:"apply"` か metadata で明示的に付ける。
- 台詞で報酬を表すときは**規定の言い回しを厳守**: `……【技術】と【センス】が上がった。`（1〜2pt=少し上がった／3〜4pt=上がった／5〜7pt=かなり上がった／8pt〜=大きく上がった）。
- 報酬目的でない地の文に、ステ名（技術/センス/根性/魅力/洞察）＋「上がった」を**偶然並べない**（誤発火する）。

### 4. 編集後セルフチェック（毎回）

台詞・設定を触ったら、コミット前に最低これを確認:

```bash
# 1) 構造リンタ（禁止語・話者ID実在・手動改行・行長・報酬キューを一括検査）
python3 tools/lint_dialogue.py            # ERROR が出たら直す（exit 1）。WARN は気付き用
python3 tools/lint_dialogue.py ch1_main   # 触ったファイルだけ部分一致で
# 2) JSONが壊れていないか（直接読むのでビルド不要）
python3 -m json.tool data/dialogue/<触ったファイル> >/dev/null
# 3) ヘッドレステスト（該当章）
```

- `tools/lint_dialogue.py` の **ERROR**（旧名・旧設定の混入／未登録 speaker／壊れた JSON）は**必ず0**にしてからコミット。
- **WARN**（手動 `\n`／全角48字超／報酬キュー）は崩れ・誤発火の温床。新規追加では出さない方針。既存の WARN（`lover_events.json` 等の手動改行）は崩れ報告が出た箇所から撤去する。

### 5. モデル差（Fable→Opus）で崩れが増える理由と対策

旧 Fable で出なかった崩れが Opus で出やすいのは、モデルの**文体傾向**が構造の弱点を突くため。性質を理解して打ち消す:

- **Opus は一文が長く・装飾的になりがち** → 全角24字の `WRAP_LIMIT` を超えやすく、自動改ページで文が割れる。**対策**: 編集時に「1台詞は全角48字以内・周囲の台詞と同じ短さで」と明示し、書いたら autoWrap 換算で字数を確認する。
- **Opus は文章を「良くしようと」言い換える** → canon の固有名詞・言い回しから逸れて矛盾・旧名復活が起きる。**対策**: 設定・固有名詞は**創作せず正本からそのまま写す**。迷ったら本節の正本表を引く。地の文の報酬表現は規定フレーズを一字一句変えない。
- **Opus は広い文脈を取り込み、古いファイルまで“正”として混ぜる** → `brand/brand` 等の旧設定を拾って propagate する。**対策**: 参照は正本に限定（`review_scope.md` のコアでも旧 brand ファイルは除外）。読み込む前に「どれが正本か」を本節で確定させる。
- 結論: 解決は「Fable に戻す」ではなく**構造を頑健にする**こと（1〜4）。正本を1つにし、改行をコードに寄せ、報酬を構造化し、コミット前 grep を必ず通せば、どのモデルでも崩れにくい。
