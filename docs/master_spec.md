## 1. 初対面キャラの名前表示「???」 [済 2026-06-12]

- まだ一度も会話していないキャラは、ネームプレート・選択肢・LIME・図鑑など
  すべての表示箇所で名前を **「???」** にする。
- 初めて会話イベントが発生した（または作中で名乗った）タイミングで実名解禁。
- 実装案: `PlayerData`（web側は save オブジェクト）に `metCharacters: Set<id>` を持ち、
  名前解決を一箇所のヘルパー関数（例 `displayName(id)`）に集約する。
  会話エンジン・LIME・日常マップの名前参照を全部このヘルパー経由に置き換える。
- シナリオ上「名乗る前から名前が分かってしまう」既存会話があれば、
  名乗りの行を入れるか「???」のままで自然になるよう微修正してよい。
- **実装メモ**: `state.flags._met_{id}` ＋ `displayName(id)`（web/js/game.js）。
  名乗りの行に `set_flag` を挿入。マップの店ピンは店名（看板）表示で、
  店主名は会うまで出ない。大会出場者はMC紹介（開始時）で解禁。

## 2. 凛（rin）訪問のコマ消費 [済 2026-06-12]

- 現状: 凛に会いに行ってもコマを消費しない（行けば行くほど得になる）。
- 変更:
  - **凛に会う（会話イベント発生）→ 1コマ消費**（他キャラ訪問と同じ扱い）
  - **買い物だけ（物販メニューのみ利用して退店）→ 消費なし**
- UI: スポット選択時に「会いに行く（コマ消費）」「買い物だけ（消費なし）」の
  分岐を出すか、店に入ってから「話しかける」を選んだ時点で消費する形でもよい。
  どちらにせよ消費タイミングがプレイヤーに分かるように表示すること。

## 3. 【バグ】夜の行動終了 → 強制バイトになる [済 2026-06-12]

- 現状: 夜のコマを消費し終えると毎回バイトに遷移してしまう。
- 正: 夜の行動が終わったら **帰宅 → 就寝 → 翌日** の流れになる。
  バイトはプレイヤーが選んだ場合のみ。
- 該当箇所: 日常ループの行動終了処理（web/js/game.js の昼夜遷移、
  Godot側は scripts/daily/）。昼→夜→翌日の状態遷移を見直すこと。
- 帰宅時に簡単な就寝演出（フェード＋「○日目 おわり」程度）があると良い。
- **実装メモ**: 原因は夜イベントの冒頭文が「閉店後の片付け」＝勤務中として
  書かれていたこと。帰宅ナイトキャップ（`night_homecoming`）を毎晩挟み、
  tonari夜イベントの冒頭を「夜、店に顔を出すと」系に書き換えた。

## 4. 会話テキストの改行ルール [済 2026-06-12]

- 人が一目で読めるのは **1行あたり約25文字** まで。これを基準に改行を入れる。
- 厳密な25文字制限ではなく **読みやすさベース**。文節の切れ目が良ければ
  26文字以上になってもよい。逆に短くても意味の切れ目で折り返してよい。
- 対応方針:
  1. 表示側: テキストボックスの自動折り返しに頼らず、データ側の `\n` を尊重する。
  2. データ側: `data/dialogue/` の既存テキストを一括チェックし、
     1行が長すぎるものに改行を挿入するスクリプト（`tools/` に追加）＋目視調整。
  3. 今後の新規シナリオもこのルールで書く（CLAUDE.md に追記すること）。
- **実装メモ**: エンジン側 `autoWrap()`（約24文字・句読点優先・禁則処理）を
  入れた。データ側の一括 \n 挿入は不要になったが、新規執筆時は意味の
  切れ目で `\n` を入れるのは引き続き推奨。

## 5. 同一店舗は1日1回まで [済 2026-06-12]

- 同じ「店」（tonari・ナルの店・アダムの店など会話イベントが起きるスポット）には
  **1日に1回しか入れない**。
- 例外: 物販ショップ（買い物のみの店）は回数制限なし。
- 訪問済みの店はマップ上でグレーアウト or「本日訪問済み」表示。
- 日付が変わったらリセット。実装は `visitedToday: Set<spotId>` で十分。
- #2 の凛の「買い物だけ」は物販扱いなので回数制限・コマ消費の対象外。

## 6. 体力（スタミナ）システム [済 2026-06-12 初版]

日常パートに体力ゲージを追加する。コンセプトは
「若いのでそこまでシビアにしない。ただし無理を重ねると寝込む」。

### パラメータ案（バランスは実装後に調整）
- 最大値 100、毎朝の起床で表示。
- **減少**: シーシャを吸う（-10〜15）、バイト（-20前後）、大会・練習（-10〜20）。
- **回復**: 夜の自然回復は1行動ぶん程度（+12）。「家に帰る」は1コマを使い、最大体力の半分ぶん（+50）回復する。
  シーシャと無関係なスポット（散歩・銭湯など）で小回復（+10〜15）する。
- **しきい値挙動**:
  - 体力 低（例: 30未満）でシーシャ関連の行動（吸う・練習・バトル）をすると
    **「くらう」/ 酸欠** が発生 → 半日（1コマ）〜1日寝込んで強制スキップ。
  - 低体力のまま数日無理を続けると **風邪** → 1〜2日行動不能、
    その後しばらくシーシャ屋を控える（シーシャ系スポット選択不可）デバフ。
- **UI**: 日常画面に常時ゲージ表示。低下時は色が変わる＋
  シーシャ系コマンドに「⚠ 今日は無理しない方がいい」系の警告を出す。
- **設計意図**: 罰ゲームではなくペース配分の要素。通常プレイで毎日全コマ
  シーシャに突っ込まなければ事故らない程度のマイルド調整にすること。
- セーブデータ互換: 既存セーブには体力=100で補完。

## 7. LIME の仕様（連投制限・小分け・選択肢返信） [部分済 2026-06-12]

- **1日1話題ルール**: 同一キャラとのLIMEは **1日に1話題のやりとりまで**。
  返事をしたのに同じ日にまた**別の話題**で送ってくるのは禁止。
- **小分け送信はOK**: 1つの話題を2〜3通に分けて送ってくるのはあり
  （「ねえ」「今日さ」「大会の話聞いた？」のような連続バブル）。
  これは1話題としてカウントする。リアルなLIME感を出す演出として推奨。
- 別キャラからのLIMEは同日でもOK。
- ストーリー進行上必要な強制イベントLIMEは例外フラグで許可
  （`forced_events.json` / `lime_events.json` 側に `ignoreDailyLimit` 等）。
- **返信は選択肢制**: プレイヤーの返信は2〜3個の選択肢から選ぶ。
  **選んだ返信によって好感度ポイント（#23）の増減が変わる**
  （例: 気の利いた返し +大 / 無難 +小 / そっけない ±0 or 微減）。
  どれが正解かは選択肢の文面から雰囲気で推測できるようにし、
  理不尽な引っかけにはしないこと。
- **残作業**: 既存LIMEの返信選択肢に増減差（pts指定）を付けるデータ作業。

## 8. 表示名はあだ名/短い呼び名のみ [済 2026-06-12]

- **ネームプレート・LIME・選択肢・通常会話文中に、フルネームは一切表示しない。**
  - あだ名があるキャラ → あだ名（あげは、みんと、なる 等）
  - あだ名がないキャラ → 下の名前など短い呼び名（例: 匂坂凛 → **「凛」**）
- フルネームは **自己紹介の台詞・設定資料としてデータに残すだけ**。
  名乗りシーンでも、台詞の中で名乗るのはOKだがネームプレートは短い呼び名のまま。
- `data/characters.json` の表示名フィールドを整理し、
  `displayName`（表示用の短い名前）と `fullName`（資料用・UI非表示）を分離すること。
- #1 の「???」解禁後に表示されるのも `displayName` の方。

- 現状キャラごとに拡大率がバラバラで見た目が変。

## 13. 吸い出し工程の「ジャスト判定」 [済 2026-06-12]

クリティカルに相当する精密入力ボーナスを吸い出し（引き）系の操作に追加する。
**※「クリティカル」という用語はゲーム内で使わない。** 統一用語は **「ジャスト」**。

- **キープ操作**: ゲージのさらに中央の狭い帯で止めると「ジャスト」
  → ブレ（揺らぎ）が大幅減少。ただしジャストでも多少はブレる（完全固定はしない）。
- **上げ / 下げ操作**: ジャストで止めると変化量が大きくなる
  （通常の上げ下げより強く効く）。
- **狙わない自由**: 大きく動かしたくない場面ではジャストを狙わず
  通常帯で止めればよい。ジャスト＝常に最適、にはしない設計。
- 演出: ジャスト成立時に専用SE＋フラッシュ＋小さなスタンプ表示。
- 既存の判定スタンプ演出（PERFECT等）と用語・見た目が混ざらないよう整理する。

## 23. 好感度システムの二層化（ポイントと段階の分離）[済 2026-06-12 基盤]

現状は「会うだけで好感度が1段階上がる」ため甘すぎる。
**内部ポイント（数値）と段階（ランク）を分離**して、攻略の手応えを作る。
- **好感度ポイント**: 隠し数値。以下で増減する。
  - キャラに会う: +（基本値。会うだけでも必ず少しは上がる）
  - 会話イベントの選択肢: 選択によって増加量が変わる（良い選択 +大 / 普通 +中 / はずれ +小 or ±0）
  - LIME返信の選択肢（#7）: 同様に変動
  - 浮気的行動（#24）: 恋人キャラに対して減少
- **段階（ランク）**: ポイントが閾値を超えると上がる。**会うたびに毎回上がるわけではない**。
  「今日は会ったけど段階は変わらなかったな」という回が自然に発生するのが正しい。
- **バランス基準**: 選択肢をそこそこ当てながら **7〜8回会えば最大段階に届く**。
  全部はずれ選択だと+2〜3回かかる程度。逆に全部正解でも5回未満では届かない
  （会う回数の下限を保証して、攻略の過程自体を遊びにする）。
- **可視化**: ステータスメニュー（#19）の人間関係タブで、段階＋次の段階までの
  ゲージ（おおまかでよい）を表示。上がった瞬間は演出を出す。
- 既存セーブの好感度段階は、対応するポイント値に変換して引き継ぐ。

  返信不要の一言タイプにして、やりとり義務を増やさないこと。

### 誠実ボーナス（隠しステータス最大の特別イベント）[未着手]
- 病み管理用の内部値（信頼度）を誠実側にも活かす:

## 25. シーシャくじ（一番くじ風の金策コンテンツ）[未着手]

ショップで引けるくじを追加する。金策になるかは引き次第、という遊び。

### 基本仕様
- ショップに「シーシャくじ」コーナーを追加。
- **第1章: 500円くじのみ**。
- **第2章以降: 500円くじ＋1,000円くじの2グレード**（家シーシャ解禁に合わせて
  1,000円くじには **台（シーシャ本体・家シーシャで使用可）** が上位賞で入る）。
- **購入回数は無制限**: ボックスの在庫がある限り、1日に何回引いてもよい。
  「毎日引かないと損」という義務感を作らないため、回数制限ではなく
  期待値設計（後述）でバランスを取る。
- 演出: 引く瞬間のドキドキ演出を必ず入れる（箱から引く→開封→ランク表示。
  上位賞は煙エフェクト＋プチュン系の特別演出。#22の品質ルール対象）。
  連続で引く時のための「結果スキップ/連続引き」も用意する。

### 賞品構成（案）
| ランク | 500円くじ | 1,000円くじ（2章〜） |
|---|---|---|
| 上位賞 | 人気フレーバー・限定グッズ | **台（シーシャ本体）**・上位機材 |
| 中位賞 | フレーバー・機材小物 | 人気フレーバー・グッズ・機材 |
| 下位賞 | 炭・ハガル等の消耗品・小物グッズ | 炭・ハガル・小物グッズ |

### 期待値の設計（重要・上位集約型）
**現金期待値はプラスにするが、価値を上位賞に集約**して、
「無限に売って引いてを繰り返す」が成立しないバランスにする。
- **現金期待値（全部売却した場合）: 還元率100〜115%** = 引き続ければ理論上は儲かる。
- **ただし分布を極端に荒くする**:
  - 下位賞の売値はほぼゼロ（数十円〜。引いた直後はほぼ確実に赤字）
  - 中位賞でとんとん弱
  - **上位賞だけがドカンと高い**（ここに期待値の大半を集約）
  - → ほとんどの引きは持ち出しで、上位賞を引いて初めて黒字化する。
    手持ち資金が薄いと上位賞に届く前に金が尽きる＝**資金（分散）が無限ループの壁**になる
- **ボックス制が利益の上限キャップ**になる:
  - 例: 500円×20枚ボックス＝投資10,000円、還元率110%なら期待利益は約+1,000円/箱
  - 補充は空後2〜3日なので、**くじで稼げる額は1サイクルあたり千円規模で頭打ち**。
    バイト1回（8,000円〜）には遠く及ばず、経済は壊れない
- **義務感も発生しない**: 引かない場合の機会損失は箱あたり千円程度に
  キャップされているので「絶対引かなきゃ」にはならない。
  引くかどうかは「上位賞のロマンを取りに行くか」の選択になる。
- 使用価値込みなら期待値はさらに上（消耗品・フレーバーを実際に使う前提）。
- 売却ルール: グッズ・機材・台は売却可 / フレーバー・炭・ハガル等の消耗品は
  売却不可（#21と整合。消耗品は使う前提の当たり）。
  **台など大物のダブり売値は低めに抑える**（台量産→売却が優位戦略にならないように）。
- `playthrough.mjs` に「ボックスを引き切り続けた場合の収支」を検証する
  テストを追加し、(a) 現金還元率が100〜115%レンジ、(b) 1ボックスあたりの
  期待利益がバイト1回の収入を大きく下回ること、の2点を確認する。

### ボックス制とラストワン賞
- くじは**ボックス制**（例: 500円くじ20枚 / 1,000円くじ12枚。残り枚数を表示）。
- ボックスの最後の1枚を引くと **ラストワン賞** を追加でもらえる。
  強さは**そこそこ**（限定グッズ・ちょっと良い機材クラス。台や激レアは入れない）。
- **補充は数日おき**（例: 空になってから2〜3日後に新ボックス）。
  空にした瞬間に次が湧くとラストワン賞の無限周回が成立してしまうため。
- 残り枚数が見えることで「あと3枚だから引き切るか」「今日はやめとくか」の
  判断が遊びになる。引き切るかどうかは完全にプレイヤーの自由で、
  引かなくても何も損しない設計を守ること。

### 演出・シナリオ連動
- **凛の口すべり**: くじ売り場の店員は凛。初回購入時などに
  「これ、実は在庫しょぶ……なんでもない」と言いかけて流す。
  **くじが実はお得であることを店側からは一切説明しない**。
- **後から誰かが教えてくれる**: 章が進んだ頃、ライバルか知り合いとの会話で
  「あのくじ、中身考えたらめちゃくちゃお得じゃね？」と教えてもらえる
  イベントを入れる（くじの存在を思い出させる自然なリマインドも兼ねる）。
  どのキャラが言うかはシナリオ側で決めてよい（なる・アダムあたりが自然）。
- **引きアニメーション必須**: ボックスに手を入れる → 紙片をつまんで引き抜く →
  めくって開封 → ランク表示、の一連を必ずアニメーションで見せる。
  上位賞は煙エフェクト＋プチュン系の特別演出、ラストワン賞は専用演出。
  連続引き時は短縮版（結果だけテンポよく並ぶ）に切り替え可能にする。
  ボックスの残り枚数が減っていく見た目（くじ紙の束が痩せる）も表現する。

### セーブ&ロード対策（リセマラ防止）
- **ボックス生成時に中身の並びを確定**する: 新しいボックスが補充された時点で
  全枚数の並び順をシャッフルしてセーブデータに保存し、引くたびに先頭から
  取り出す方式にする。**引く直前にセーブ→ロードしても結果は変わらない**。
- 引いた直後にオートセーブを挟み、引き逃げ（結果を見てからロード）も防ぐ。
- **ゲーム内での説明は凛のメタ発言でやる**: リセマラを試みそうな文脈
  （くじ説明時や連続で引いた時など）で凛が
  「あ、セーブしてやり直しても出るもの同じだから。そういうふうにできてるの」
  くらいの軽いメタ台詞をさらっと言う。世界観を壊さない一言サイズに留め、
  くどく繰り返さないこと（言うのは1回でいい）。

### データ化
- 賞品テーブル・確率・ボックス構成は `data/kuji.json`（新規）に定義し、
  章ごとのラインナップ差し替えをデータだけでできるようにする。

## 26. LIME交換の流れを全キャラ自然にする（誠実な連絡先管理）[部分済 2026-06-12]

LIMEが届く全キャラについて、**「いつ・なぜ連絡先を交換したのか」が
作中で必ず描かれている**状態にする。理由なくLIMEを持っているキャラを無くす。

### 原則
- **自動入手の禁止**: LIME交換は必ず作中の出来事（交換イベント）として描く。
  章が進んだら勝手に追加されている、初対面なのにLIMEが来る、は禁止。
- **交換前はLIMEアプリに表示されない**（#1の「???」と同様、知らない人は
  連絡先一覧にも存在しない）。
- **交換の理由がそのキャラの関係性として自然であること**:
  - バイト仲間・店関係 → シフトや業務連絡のため
  - ライバル → 大会の連絡網・対戦をきっかけにした交換
  - ヒロイン → 関係が一歩進むきっかけイベントの中で
  - 常連客 → ある程度通って親しくなってから
- **交換イベント自体を小さなキャラ回にする**: 交換のしかたにキャラを出す
  （あげはなら向こうからグイグイ、寡黙なキャラなら無言でQR画面を差し出す、等）。
  ヒロインの場合、交換は好感度の節目イベントとして配置してよい。

### 既存データの監査と修正

  彼女らしい無口な交換のしかたにする）。

  強制イベント含めLIMEが届かないようガードを入れる）。
- **実装メモ**: web側は従来の `LIME_EXCHANGE_VISITS`（交換シーンのある訪問回数）を
  ガードとして流用中。噂LIME（業界の重鎮など affinity 管理外）は例外。
  つむぎ等の交換専用イベント執筆は残作業。

## 1. アルミ穴あけパート — HOLE RHYTHM BATTLE

### 概要
アルミの円盤上をカーソルが円周状に回転し、タイミングよく穴を開けるミニゲーム。
メイン評価は **「穴をどれだけ均等に、美しく開けられたか」**。
穴数や位置は後工程のシーシャ性能にも影響するが、スコアの最重視は均等度。

### 画面仕様
- 中央に円形のアルミ盤
- 外周・中周・内周の3リング
- カーソルが現在のリング上を時計回りに回転
- 入力すると現在位置に穴が開く（黒い小さな点/丸で仮表示）
- 残り時間・現在リング・スコア・コンボを表示

### 操作
- Space / クリック / タップ: 穴を開ける
- Enter / 完成ボタン: 穴あけ終了
- 外周がある程度完成したら中周へ、中周がある程度完成したら内周へ移動
- 内周は開けすぎるとリスク上昇

### 評価項目とスコア比率
均等度 / 円形精度 / 穴サイズ安定 / 過密ペナルティ / 空白ペナルティ /
リング完成度 / 残り時間ボーナス

```text
穴あけスコア =
均等度 50%
+ 円形精度 20%
+ 穴サイズ安定 15%
+ リング完成度 10%
+ 残り時間ボーナス 5%
```

### 穴数による性能影響
穴が多い: ドロー↑ 煙量↑ 立ち上がり早 / 熱保持↓ 焦げリスク↑ 灰落ちリスク↑
穴が少ない: ドロー重 煙量↓ 立ち上がり遅 / 熱保持↑ 灰落ちリスク↓

### リング別の役割
```text
外周: 熱拡散、安定感、持続力
中周: ドロー、煙量、立ち上がり
内周: 抜け感、攻め要素、焦げリスク
```

### レモン大会での理想
外周: 多め・均等 / 中周: 普通 / 内周: 少なめ
（レモンの香りは熱で飛びやすい → 熱を全体に広げ、中心火力を強くしすぎない）

### 演出テキスト（定数化）
PERFECT / GOOD / BEAUTIFUL RING / AIR FLOW UP / RING COMPLETE /
TOO CLOSE / BLANK SPACE / TOO MANY / RISKY

## 2. 炭焼きパート — HEAT IGNITION

### 概要
炭の色・赤熱具合・灰の状態を**目で見て**、ベストタイミングで取り上げるミニゲーム。
**ゲージ停止ゲームではない**。炭の見た目を観察して判断するゲームにすること。
ジャストタイミングに入った瞬間、**炭の芯そのものが一瞬ピカッと光る**。
その瞬間に取ると最高評価。

### 画面仕様
- 炭を3つ表示。炭ごとに焼けるスピードを少し変える
- 時間経過: 黒 → 赤 → 赤熱 → **ピカン** → 白熱 → 灰かぶり

### 操作
- クリック / タップ: その炭を取り上げる
- 長押し / 右クリック: 炭を裏返す（後回しでよい。最初は「取る」だけで成立させる）

### 炭の状態と評価
| 状態 | 見た目 | 評価 | 影響 |
|---|---|---|---|
| 生焼け | 黒い芯が残る | 低 | 火力不足、立ち上がり遅 |
| 早取り | 端だけ赤い | やや低 | 焦げにくいが煙量不足 |
| 適温前 | 全体が赤くなり始め | テーマ次第で良 | 香り保持高、火力控えめ |
| **ジャスト** | 赤熱＋芯が一瞬ピカッ | **最高** | 火力安定、香り保持、立ち上がり良好 |
| 攻め焼き | 白っぽく赤い | 煙量重視なら有利 | 煙量↑ 焦げリスク↑ 香り保持↓ |
| 焼きすぎ | 灰被り・白すぎ | 低 | 熱暴走、香り飛び、焦げリスク高 |

### ピカン演出
- ジャスト付近で炭そのものが一瞬光る
- 光った瞬間に取る → 「JUST IGNITION!!」
- 早すぎ → 「CORE BLACK」 / 遅すぎ → 「OVER HEAT」
演出テキスト: JUST IGNITION!! / 赤熱一閃 / CORE BLACK / OVER HEAT /
HEAT STABLE / AROMA KEEP

### 性能影響の数値例
```json
早取り:   { "heatPower": -20, "heatStability": -10, "startupSpeed": -20, "burnRisk": -15, "aromaRetention": 10 }
ジャスト: { "heatPower": 20,  "heatStability": 30,  "startupSpeed": 15,  "burnRisk": 0,   "aromaRetention": 15 }
焼きすぎ: { "heatPower": 35,  "heatStability": -10, "startupSpeed": 25,  "burnRisk": 30,  "aromaRetention": -20 }
```

### レモン大会での理想
ジャスト直前〜ジャスト。
（煙量よりも香り保持と焦げリスクの低さを重視する）

## 3. プレゼン／審査パート — FLAVOR TRIAL

> **用語注記（第1部 #17）**: 本パートの正式用語は
> **「コンセプト」（制作前に選ぶ方針）と「アピールポイント」（制作実績の持ちネタ）**、
> 動詞は**「ぶつける」**。旧仕様にあった弾丸系の呼称はすべて廃止済みで、
> コード・UI・テキストのどこにも残さない。
> 審査員への反論ワードも「嘘だ！」→「香ってない！」「ズレてる！」等の
> 味・香り基準に統一する。実装時は `data/glossary.json` に正式登録すること。

### 概要
作る前に決めた「方針」と、完成したシーシャのステータスが一致しているかを
審査員に証明するバトル。単なる会話ゲームではなく、
**「言ったこと」と「作ったもの」が一致しているかを判定するゲーム**にする。

### 基本の流れ
```text
1. 大会レギュレーション発表
2. プレイヤーが方針を2〜3個選ぶ
3. シーシャ制作パート
4. 完成品ステータス確定
5. コンセプトとアピールポイントを持って審査へ
6. 審査員のザワザワ発言にアピールポイントをぶつける
7. 一致 → 納得ゲージ上昇 / 乖離 → 「香ってない！」と反論される
```

### コンセプト（制作前に選ぶ今回の方針）
香り重視 / 煙多め / リラックス / スピード提供 / 味濃いめ / 持続力重視 / 独創性重視

### アピールポイント（制作結果から自動生成される実績）
外周穴が均等 / 穴あけ評価A / 内周控えめ / ジャスト炭 / 炭ピカン成功 /
火力安定A / レモン香A / 煙量A / 焦げリスク低め / 残り時間ボーナス

### 審査員のザワザワ発言例
```text
「レモンの香りはちゃんと残っているのか？」
「煙量は少し弱いのでは？」
「早く作った分、完成度が落ちていないか？」
「リラックス系と言うには刺激が強くないか？」
「味濃いめと言うには主張が弱くないか？」
```

### 成功/失敗の判定例
成功: 方針=香り重視、完成品レモン香88・香り保持82・焦げ12、
手持ちアピールポイント=ジャスト炭/内周控えめ → ぶつける: 香り重視＋レモン香A＋ジャスト炭
→ 「確かに言ってる通りだ！」納得ゲージ上昇
失敗: 方針=香り重視、完成品レモン香35・焦げ65・炭焼きすぎ → ぶつける: 香り重視
→ 「香ってない！」「煙は出ているが、レモンの香りは飛んでいる！」納得ゲージ低下

### 評価軸
```json
{
  "logic": "方針と完成品が一致しているか",
  "evidence": "アピールポイントが実際の結果に基づいているか",
  "timing": "審査員の発言に合ったアピールポイントをぶつけられたか",
  "persuasiveness": "納得ゲージをどれだけ上げたか"
}
```
成功演出: 納得！ / 確かに言ってる通りだ！ / FLAVOR SYNC!!
失敗演出: 香ってない！ / 意図と味がズレている！ / SESSION BREAK

## 4. 結果発表10カウント — RESULT 10 COUNT

### 基本の流れ
審査終了 → 集計中…… → 会場ザワザワ → RESULT 10 COUNT →
10…9…8…（カットイン挟みつつ）…1…0 → 順位に応じた演出分岐。
カウント中カットイン: 主人公の真剣な顔 / アルミ穴あけ / 炭のピカン /
ジャスト炭 / 煙 / レモン / 審査員の目元 / 会場のざわめき

### 順位別演出
| 結果 | 演出 |
|---|---|
| **1位通常** | 0でプチュン → 暗転 → 無音 → 白煙 → 審査員4分割カットイン → PERFECT SESSION → 優勝おめでとう |
| **1位プレミア** | 超高評価時、**2〜3秒残しでフライングプチュン** → PERFECT SESSION → 完全優勝 |
| **2位** | プチュ……白煙が出かける → **パリン** → 第2位（惜しい演出。完全プチュンは起こさない） |
| **3位以下** | 0で即パリン → 黒煙 → 順位表示 |
| **大失敗** | ヒビ → バキン！！ → 黒煙 → OVER HEAT → 順位表示 |

## 8. 実装時の注意

- 既存に似たパートがある場合は、本仕様を優先して差し替える

- 各パートは関数またはクラスとして分離する
- GameState に結果を保存し、次パートへ引き継ぐ
- 「スタイリッシュ職人バトル」の雰囲気を最重視する
